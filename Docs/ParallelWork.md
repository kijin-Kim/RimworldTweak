# 병렬 작업 계획

작성일: 2026-11-15. 작업 0-A 완료 이후의 개발 계획이다. 0-B와 0-E1을 병렬 구현·검증 완료했다. 이후 작업의 완료 여부는 Status.md를 따른다.

## 원칙과 범위

- Computer Use, 브라우저·데스크톱 UI 자동화를 사용하지 않는다. 이를 다른 UI 자동화 도구로 우회하지 않는다.
- 코드·파일·명령줄을 통해 작성·검증한다. Unity Test Framework, Editor 스크립트, 빌드·실행 로그를 활용할 수 있으나 0-E1의 Edit Mode CLI 실행기는 구현했다. Play Mode·빌드 도구는 후속 범위다.
- 같은 작업 폴더의 코드 작성은 소유권을 나누어 병렬화한다. Unity import·컴파일·테스트·빌드·실행 검사는 통합 담당자가 단일 큐로 처리한다.
- 시각·조작 검증 기준은 없애지 않는다. 생성된 실제 렌더 이미지의 정적 검토와 사용자 수동 플레이를 구분하고, 증거가 없으면 미검증으로 남긴다.
- Git은 main으로 초기화했지만 공유 작업 폴더를 유지한다. worktree나 merge로 격리되어 있다고 가정하지 않는다. 최초 기준 커밋 1회 이후 커밋은 재승인이 필요하며 원격 연결·push는 금지한다.

## 공유 폴더 유지와 워크트리 전환 검토

2026-11-15 사용자 결정: **작업 0은 공유 폴더 방식으로 유지한다.** 아래 기준은 이후 전환을 검토하기 위한 것이며 워크트리 생성, Git 초기화 또는 커밋을 승인한 것은 아니다.

### 검토 시점

1. **작업 0 종료 후, 작업 1 착수 전:** 공통 계약의 안정성, 병렬 작성 중 발생한 대기·충돌, 검사 소요 시간을 바탕으로 첫 검토를 한다. 작업 0 완료만으로 자동 전환하지 않는다.
2. **작업 3 통과 후, 작업 4 건설과 작업 5 생산을 병렬 배정하기 전:** 자원·예약·통행 계약 위에서 독립 기능을 지속적으로 나눌 수 있는지 확인하고 다시 검토한다.
3. 이후에는 검증 대기, 변경 혼입 또는 복구 어려움이 반복되면 다음 기능 묶음을 배정하기 전에 추가 검토한다. 작업 도중 즉흥적으로 폴더를 분리하지 않는다.

### 판단 기준과 남길 증거

| 판단 항목 | 공유 방식 유지에 유리 | 워크트리 검토에 유리 | 기록할 내용 |
|---|---|---|---|
| 기능 간 의존성 | 공통 계약이 자주 바뀌고 함께 수정해야 함 | 안정된 계약 위에서 독립된 기능을 작성 가능 | 공동 수정 파일, 계약 변경과 재작업 사례 |
| 검증 대기 | 검증이 짧고 다른 준비 작업으로 대기 흡수 가능 | 한 기능의 검사 때문에 무관한 기능 작성까지 반복 중단 | 동결 시간, 중단한 작업과 이유 |
| 변경 분리 | 파일 소유권만으로 변경 범위를 명확히 구분 가능 | 미완성 변경이 섞여 원인 분석·검토·되돌리기 어려움 | 혼입·덮어쓰기·복구 사례와 추가 작업 |

| 통합 준비 | 기준 상태와 통합 절차가 아직 없음 | 검증된 기준 상태와 브랜치별 검토·통합 절차를 마련 가능 | 기준 검증 결과, 변경 전달·통합 방법 |

단순히 에이전트 수가 늘거나 기능 수가 많아졌다는 이유만으로 전환하지 않는다. 독립 기능의 존재와 실제 대기·혼입 비용을 우선 평가한다. 현재 비용은 측정되지 않았으며 고정된 시간 절감률이나 전환 임계값을 가정하지 않는다.

### 전환을 선택할 경우의 운영안

- 검증된 기준 커밋과 브랜치·통합 방식을 먼저 마련해야 한다. 최초 기준 커밋 1회만 승인되어 있으므로, 실제 전환 전에 워크트리 생성·브랜치 운영·후속 작업 커밋의 허용 범위를 사용자와 확정한다.
- 통합용 폴더와 소수의 기능별 워크트리부터 시작한다. 각 기능 변경을 따로 검토한 뒤 통합하고, 합친 상태에서 회귀 검사를 다시 실행한다.
- 파일 소유권, 공통 Scene·설정의 단일 담당, 원본과 .meta의 동시 관리 및 GUID 보존 규칙을 유지한다. 워크트리는 의미상 충돌까지 해결하지 않는다.
- Unity로 여는 각 워크트리는 별도 Library를 사용한다. 같은 프로젝트 경로의 동시 실행 금지는 유지한다. 처음에는 서로 다른 워크트리의 Unity 검사도 순차 실행하고, 자원 사용과 이득을 측정한 뒤 동시 실행 여부를 별도로 결정한다.
- 검사 중인 워크트리의 입력은 동결한다. 다른 워크트리에서는 독립 기능 작성을 계속할 수 있지만 검사 대상에 변경을 반영하지 않는다.
- 실제 전환 시 이 문서의 공유 폴더 전제와 실행·소유권 규칙을 갱신하고 검토 근거와 선택 이유를 결정 기록에 남긴다. 이번 수정에서는 전환을 실행하지 않는다.

## 먼저 확정할 공통 계약

통합 담당자가 [초기 월드 계약](Contracts/InitialWorld.md)을 확정하고 참여자가 읽은 뒤 0-B/0-E1을 병렬 구현했다. C/D의 구체적 Runtime 접점은 착수 시 확인한다.

1. 초기 시나리오의 타일 크기·ID·좌표·초기 자원, 중복 ID와 맵 밖 위치의 오류 반환 방식.
2. 월드가 초기 입력을 소유하는 방식과 외부 변경 격리, 읽기 상태의 접근 범위.
3. 시간 단위와 Tick 전달, 초기화·재시작 시 객체 교체 및 화면 재연결 책임.
4. 각 asmdef 참조 방향, 테스트 이름·실행 필터, 파일 소유권 목록.

이는 변수별 작업 분할이 아니라 기능 간 접점을 고정하는 준비다. 병렬 작업을 위해 범용 프레임워크나 별도 복제 프로젝트를 만들지 않는다. 계약 변경이 필요하면 영향 작업만 잠시 멈추고 관련 소유자가 합의한 뒤 함께 수정한다.

## 담당자와 수정 경계

| 역할 | 주된 소유 범위 | 직접 수정하지 않는 범위 |

| 검증 담당 | 테스트 코드, Tools 실행 스크립트, 검사 사양 | 제품 코드·실제 Unity 실행·공유 설정 |

P1에서는 시뮬레이션과 검증 작성 2개 축을 사용한다. P2에서는 root가 D를 맡고 표시·검증 담당을 병렬 배치한다. 빈 역할을 채우기 위해 불필요한 에이전트를 계속 실행하지 않는다.

- B가 끝나면 변경한 파일 목록·계약·남은 제약을 인계한다. D에 필요한 Simulation 시간 관련 수정은 인계 후 root가 맡는다. B 담당과 D 담당이 같은 파일을 동시 수정하지 않는다.
- .meta는 원본 파일의 소유자를 따른다. 공유 asmdef, Scene, Settings는 통합 담당만 수정한다. GUID를 임의로 재생성하거나 Library를 소스로 복사하지 않는다.
- 소유권은 폴더명만으로 추정하지 않고 각 작업 시작 때 파일 범위를 명시한다. 테스트 asmdef도 통합 담당이 먼저 배치한다.
- 검토자는 읽기와 메시지로 반론을 전달한다. 다른 소유자의 파일을 몰래 수정하거나 덮어쓰지 않는다.

## Unity 실행 직렬화

검사 실행 전 담당자 전원이 변경 완료를 알리고 Assets, Packages, ProjectSettings, 실행 스크립트, 선택한 시나리오의 쓰기를 동결한다. 검사 중에는 분리된 문서·검토 보고서 작성만 병렬로 한다.

통합 담당자는 같은 경로를 사용하는 에디터·테스트·빌드가 없는지 확인한다. 열려 있는 사용자 에디터를 강제 종료하지 않는다. 정상 종료가 필요하면 사용자에게 알리고, 실행할 수 없으면 이유를 기록한다. 잠금을 삭제하거나 사용 중인 Library를 다른 프로세스로 강제 공유하지 않는다.

각 실행에는 고유 결과 폴더를 사용하고 에디터 버전, 패키지 기준, 입력 파일 해시, 검사 수·실패·누락, 시작·종료 상태를 기록한다. 검사가 끝나면 동결을 풀고 실패 원인에 해당하는 소유자에게 수정 요청한다. 0-E1 실행기에 고유 결과·입력 해시·잠금·결과 판정을 구현했다. 실제 운영 장애의 강제 재현 여부는 검증 기록에 구분한다.

## 0-C/D/E2/F 실제 배정

[DemoRuntime 계약](Contracts/DemoRuntime.md)을 먼저 확정하고 demo_runtime, demo_view, demo_tests가 각각 시간·수명, 표시, 검사를 병렬 작성했다. 소유권은 해당 계약을 따른다. 작성 종료 후 root에게 인계하고 소스 쓰기를 동결했다. root만 Prepare → EditMode → PlayMode → Build → Smoke를 직렬 실행한다. [교차 검토 기록](Reviews/2026-11-15-demo-review.md)과 실제 검증 기록은 구분한다.

## 작업 1 실제 배정

[MovementTime 계약](Contracts/MovementTime.md)을 먼저 고정했다. movement_sim은 Simulation 상태·경로·명령, movement_view는 표시·선택·입력, movement_tests는 검사를 병렬 작성한다. root는 Runtime 시간·명령 전달, Player smoke, 공유 asmdef·설정·문서를 맡는다. 각 담당 파일 소유권은 계약 표에 명시했고 Unity 실행은 root만 직렬 수행한다.

## 작업2 실제 배정

[생활 공통 계약](Contracts/Living.md)을 먼저 확정했다. life_sim은 Simulation 전반과 예약·욕구·생활 상태, life_view는 표시·입력 피드백, life_tests는 상태·통합 검사를 단독 소유한다. root는 Runtime 기본 시나리오와 Player smoke·공유설정·문서를 맡는다. 작성은 병렬, Unity 실행은 쓰기 동결 후 root가 직렬 수행한다.


작업2 현재 상태 정정: 최신 요청은 계획 정리만이다. 위 배정으로 작성된 초안은 추가 수정과 실행을 중단했으며 검증되지 않았다. 생활 계약은 승인된 계약이 아닌 초안으로 취급한다. 향후 구현 승인 전 병렬 작업을 재개하지 않는다.

작업2 재개: 사용자가 구현 목표를 active로 전환했다. 기존 소유권을 유지하고 life_sim/life_tests/life_view 교차 검토 후 root 통합 검증을 진행한다. 검토 중 발견한 수면 중 침대 삭제 복구와 테스트 누락을 보완한다.
