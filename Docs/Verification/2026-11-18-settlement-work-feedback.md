# 250칸 정착지와 폰 작업 표시 검증

## 구현 내용

시작 폰과 초기 자원·침대·채집물의 상대 배치를 유지하며 새 정착지를 중앙에 만든다. 새 게임 카메라는 첫 폰을 중심으로 주변을 보여준다. 맵 경로 탐색은 출발점과 지형 버전이 같으면 앞에서 탐색한 범위를 이어 사용한다. 땅은 처음 한 번 일괄 채우고 장애물이 변하면 해당 칸을 갱신한다. 구역 바닥은 구역당 타일맵으로 그린다.

실제 작업자의 점유 및 행동과 대상의 진행값을 한 번에 읽는다. 같은 화로의 계획서가 여러 개여도 현재 진행 중인 한 끼를 표시한다. 건설·철거·벌목은 내리치고 조리는 가볍게, 파종·수확·식물 채집은 더 깊게 숙인다. 각도와 높이는 발 접점을 기준으로 계산한다. 표시 시간은 저장되는 시뮬레이션 틱과 남은 시간에서 얻는다.

## 실제 플레이 확인

[검증용 게임 실행](../../TestResults/WorkFeedbackManual/Play.cmd)은 전용 저장 폴더로 Windows Player를 실행한다. 제품 실행 파일은 `Builds/Windows/RimworldTweak.exe`다. 직접 실행하면 평소 게임 저장 폴더를 사용한다.

1. 새 정착지를 시작한다. 첫 화면에서 시작 폰과 가까운 자원을 찾고, 폰 선택·맵 확대와 축소·가장자리 이동 후 초상을 통한 위치 보기를 확인한다.
2. Esc → 불러오기에서 **작업 표시 확인**을 연다. 정지된 250×250 장면에 화로 앞의 조리 폰, 나무와 식물에서 작업하는 두 폰이 있다. 화로 진행값은 8/40이고 채집 두 건은 각각 4틱이다. 기본 배율에서 어느 폰이 어느 대상을 작업하는지와 세 막대를 구분할 수 있는지 본다.
3. 1배속 → 정지 → 3배속을 바꾼다. 정지 중에는 발과 막대가 멈추고, 재생하면 폰이 화로 쪽으로 숙이거나 나무를 내리치고 식물에 몸을 숙인다. 빠른 배속에서 눈에 거슬리는 떨림, 발 미끄러짐, 이름표 가림이 있는지 본다.
4. 채집이나 조리 중인 폰을 선택하고 소집하면 그 폰의 막대와 동작이 사라져야 한다. 새 이름으로 저장하고 게임을 종료한 뒤 같은 검증용 실행으로 이어하기를 누르면 저장한 작업과 진행 상태를 다시 볼 수 있다.

회신 예시는 “모두 정상” 또는 “3배속에서 벌목하는 폰만 발이 흔들려”다.

## 검토 중 재현한 문제와 수정

- 첫 EditMode에서 16MiB를 넘는 데이터 덮어쓰기 시험이 실패했다. Unity Mono 직렬화기가 용량 예외를 TargetInvocationException으로 감싸는 경우를 처리했다. 덮어쓰기 실패가 정상 반환되고 기존 슬롯 바이트와 읽기 결과가 보존되는지 검사한다.
- 첫 PlayMode에서 (249,249) 바닥 타일이 비어 있었다. 정확한 250×250 경계를 지정해 타일 블록을 초기화하도록 수정했다. 모서리의 원래 타일 → 장애물 → 원래 타일과 전체 바닥 갱신 횟수를 검사한다.
- 첫 Windows 성능 검사에서 250칸 맵 코너 탐색은 18.0ms, 세 폰의 가장자리 명령은 41.3ms였다. 32×32 밭 확정은 0.14ms였으나 이후 첫 화면까지 141.2ms가 걸렸다. 셀마다 생기는 동일 알림을 경작 구역과 사유 단위로 모아 영향받는 칸 수를 표시하고, 누르면 대표 작물 칸으로 이동한다. 길찾기는 정수 배열 기반의 동일 순서 탐색으로 변경하고 도달 여부 검사에서는 경로 리스트 생성을 생략했다. 250칸 이하 맵에 적용하며, 더 큰 사용자 시나리오는 기존 희소 탐색 경로를 유지한다.

## 자동 검사와 Windows 실행 결과

- 최종 EditMode 198/198 (`20261118T050913375Z-1600b73d`), PlayMode 119/119 (`20261118T050958517Z-7750e022`). 기존 저장과 250칸 경계, 실제 작업 소유자와 진행값, 다른 폰의 진단 조회, 막힘·소집·복원, 몸체·발 위치와 방향, 게이지 위치·채움, 그룹화된 밭 알림과 선택을 확인했다.
- 최종 Windows 일반 빌드 `20261118T051113717Z-build` 성공. 검사와 빌드는 소스·에셋·설정·검사 도구를 동결한 상태로 직렬 실행했다.
- Windows 측정 환경은 AMD Ryzen 5 5600, 1280×720, UI 150%, 3명이다. 아래는 일반 빌드 한 차례 측정이다. 구역은 32칸 시험 맵에서 8×8, 250칸에서 32×32였다. 프레임 값은 측정 동작을 시작해 다음 프레임에 진단 코루틴이 재개될 때까지의 경과 시간이다. 원본은 `TestResults/20261118T051203452Z-ux-mapperformance/map-performance/performance-{32,250}.json`에 있다.

## 복원·렌더링·메모리 근거

- 새 정착지 메뉴로 만든 250칸 맵에서 (249,248)을 막고, 한 폰은 채집하고 다른 폰은 (249,249)로 이동 중인 28틱에 저장했다. 저장 Player PID 13708과 별도 복원 Player PID 34208에서 작업과 이동을 마친 2,130틱의 전체 상태 해시가 일치했다. 실제 결과는 `map-work-20261118T051246782-save`, `map-work-20261118T051254482-load`에 있다.
- 기존 제품 DLL로 만든 32×32 이름 있는 슬롯과 저장소의 10×10 legacy-v1 파일을 새 Windows Player가 모두 열었다 (`map-work-20261118T051302148-legacy-map`). 검증용 게임의 전용 슬롯도 최종 빌드 DLL로 읽어 250칸, 173틱, 조리 8/40과 두 채집 작업 진행 4틱을 확인했다.
- 1280×720/UI 150% (`20261118T051228716Z-ux-workfeedback`)와 1920×1080/UI 100% (`20261118T051237280Z-ux-workfeedback`) 각각 6개 진단 렌더와 화면 배치 검사를 통과했다. 조리 시작·절반·완료, 이웃 작업 둘, 멀리 축소한 선택 폰, 하단 명령 패널 가까이의 건설·이동 경로를 담았다. 일반 UI 32장면과 저장·복원 2장면을 더한 46개 배치 보고서의 이슈는 0이었다. 네이티브 창 자동 캡처는 이 환경에서 단색이었다. 화면 검토에는 같은 엔진의 지도 카메라와 HUD를 합성한 별도 렌더를 사용했다.
- 일반 배포 Player에서는 프레임 할당 카운터를 제공하지 않아 `-1`로 기록한다. 별도 개발용 Windows Player로 같은 장면의 프레임 전체 GC 할당을 측정했다 (`work-gc-20261118T051408679`). 250칸 맵에서 모서리 경로 15,800B, 1,024칸 밭 생성 234,502B, 최초 파종 선택 737,484B, 동기 슬롯 저장 19,027,298B였다. 파종 후보마다 경로를 보관하던 버전의 같은 프레임은 7,090,116B였다. 프레임 값에는 같은 프레임의 UI와 엔진 작업도 포함된다.
- 구현, 자동 검사, 빌드, 저장 재실행, 성능 측정과 진단 화면 검토를 마쳤다. 실제 창에서의 읽기 편함과 3배속 동작 체감은 사용자 확인 대기다.
