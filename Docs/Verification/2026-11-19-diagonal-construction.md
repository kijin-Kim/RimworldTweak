# 대각선 이동과 건설 대기 검증

정착민과 습격자가 열린 땅에서 대각선으로 이동하고 벽 모서리에서는 돌아간다. 네 건물의 설계도 위에 폰이 서면 반입재와 공정이 그대로 남고, 현장이 빈 다음 건설 틱부터 다시 진행한다. [기능별 완료 기준](../Plans/Diagonal-Movement-Construction.md)

## 게임에서 직접 확인

1. [전용 저장으로 실행](../../TestResults/DiagonalManual/Play.cmd) 후 **이어하기**를 누른다. 열리는 저장의 이름은 **대각 이동과 공사 대기**다. 실행 파일은 [RimworldTweak.exe](../../Builds/Windows/RimworldTweak.exe)이며 실행 스크립트가 검증용 저장 경로를 지정한다.
2. 가운데 겹친 정착민과 설계도를 눌러 **같은 칸 대상**에서 **벽 설계도**를 선택한다. 목재 2/2, 시공 23/40, **현장 비우기 대기**가 보인다. 1배속으로 재생해도 그 칸에 정착민 2가 있는 동안 값이 그대로여야 한다.
3. 위쪽 초상에서 **정착민 2**를 선택하고 오른쪽 위로 가로·세로 두 칸씩 떨어진 빈칸을 우클릭해 이동을 지시한다. 상황 메뉴가 열리면 **선택한 정착민 이동**을 누른다. 이미 소집되어 있다. 대각선으로 빠져나가면 정착민 1이 공사를 재개하고 벽 하나가 완성된다.
4. 정착민 2를 완성된 벽의 왼쪽 칸으로 보낸 뒤 벽 위쪽 칸으로 이동을 지시한다. 두 칸은 대각선으로 붙어 있지만 사이 모서리에 벽이 있어 위로 한 칸, 오른쪽으로 한 칸 돌아간다. 넓은 빈 땅에서 같은 방향으로 이동시키면 곧바로 대각선으로 걷는다. 정지와 3배속으로도 비교할 수 있다.

회신 예시는 “대각 이동·벽 우회·건설 재개 모두 정상” 또는 “2번에서 현장을 비웠는데도 진행값이 그대로야”다. 자동 조작과 렌더 확인은 아래 결과에, 실제 마우스·키보드 체감은 사람 확인으로 따로 기록한다.

## 일반 Windows Player 성능

같은 PC, 1280×720, UI 150%, 같은 지도·폰 수·명령에서 준비 실행 한 번 뒤 새 프로세스로 5회 측정했다. 표는 메인 스레드 작업 시간의 중앙값·최댓값(ms)이다. 접근 불가 장면은 목적지는 비어 있고 네 면이 둘러싸인 경우다.

| 지도 | 동작 | 변경 전 중앙값 / 최대 | 변경 후 중앙값 / 최대 |
|---|---|---:|---:|
| 32×32 | 모서리 경로 | 0.151 / 0.182 | 0.307 / 0.326 |
| 32×32 | 세 폰 이동 | 1.345 / 1.375 | 1.346 / 1.421 |
| 32×32 | 고립 목적지 | 0.081 / 0.085 | 0.066 / 0.082 |
| 32×32 | 밭 작업 선택 | 0.958 / 0.995 | 1.006 / 1.034 |
| 250×250 | 모서리 경로 | 0.618 / 1.054 | 1.004 / 1.149 |
| 250×250 | 세 폰 이동 | 2.882 / 3.135 | 0.111 / 0.134 |
| 250×250 | 고립 목적지 | 0.869 / 1.024 | 0.002 / 0.003 |
| 250×250 | 1,024칸 밭 작업 선택 | 15.237 / 15.453 | 18.476 / 19.411 |

첫 구현의 먼 목적지 탐색은 재검토선을 넘었다. 방향별 최소 남은 시간을 이용하는 A*를 먼 단일 경로에 적용하고, 고립 목적지는 열린 옆 칸 유무로 걸렀다. 한 출발점에서 밭의 여러 후보까지 찾을 때는 다익스트라 탐색을 이어 쓴다. 위 일반 빌드의 최종 측정에는 중앙값이 두 배를 넘으면서 1ms 이상 증가한 항목이 없었다. 250폭 밭 작업 선택은 중앙값 기준 약 3.24ms 더 걸렸다. [측정 원본 목록](../../TestResults/DiagonalBaseline/after-runs.txt)

## 개발 빌드의 습격 추적과 메모리

변경 전 기준 커밋 `de130122`의 제품 입력을 임시 디렉터리에 풀고, 변경 후와 같은 두 습격자·20틱 측정 코드를 추가해 개발용 Player를 만들었다. 전후 같은 해상도·장면을 각각 준비 1회, 측정 5회 실행했다. 할당은 해당 프레임 전체의 중앙값이며 UI·엔진·첫 탐색 배열 생성도 포함한다.

| 지도·장면 | 처리시간 중앙값 / 최대, 변경 전 → 후 (ms) | 프레임 할당 중앙값, 변경 전 → 후 |
|---|---:|---:|
| 32폭 습격 20틱 | 4.685 / 4.744 → 4.806 / 4.852 | 342,482 → 205,810 B |
| 250폭 습격 20틱 | 10.508 / 11.909 → 3.009 / 3.110 | 1,485,738 → 2,751,722 B |
| 250폭 모서리 조회 | 0.692 / 0.771 → 1.001 / 2.103 | 19,032 → 1,172,936 B |
| 250폭 세 폰 이동 | 2.814 / 3.106 → 0.140 / 1.193 | 44,612 → 39,534 B |
| 250폭 밭 선택 | 15.693 / 16.029 → 19.061 / 20.546 | 746,018 → 779,848 B |

큰 지도의 첫 장거리 탐색은 월드가 재사용할 배열을 별도로 만들기 때문에 그 프레임의 할당이 증가했다. 반복 사용한 세 폰 명령과 새 월드의 첫 경로는 구분해 기록했다. 개발 빌드 시간 측정에서도 재검토선을 넘은 항목은 없었다. 최종 배포 빌드의 입력 546개와 출력 185개를 개발 빌드 검사 뒤 다시 대조해 해시 일치를 확인했다. 직접 확인용 실행 스크립트는 검증용 저장 폴더를 사용한다. 사람의 직접 조작 결과는 아직 접수하지 않았다.

같은 배포 DLL에서 습격자가 대각선을 6/7 진행했을 때 옆 칸의 통행을 막고 한 틱을 진행했다. 습격자는 원래 칸에 머물고 다음 걸음이 직교로 바뀌었으며 그 즉시 만든 저장을 다시 열 수 있었다. [통행 변경 경계 기록](../../TestResults/DiagonalBaseline/raider-closed-side.json)
