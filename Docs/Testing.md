# 검증 계획과 증거 기록

이 문서의 검사는 계획이다. 실행 결과는 [Status.md](Status.md)에 링크하며 아직 실행하지 않은 검사는 통과로 표시하지 않는다.

## 현재 저장·UI·아트 검증 범위

2026-11-17 후속 범위는 [요구사항별 완료·검증 기준](Plans/SaveLoad-UX-Art-Acceptance.md)을 따른다. 저장 실패/기존 호환/재실행, UI 입력·시간 차단, 기존 명령 이관, 아트 교체·표시·12해상도/배율 조합을 관측 조건과 연결했다. 아래 T8 자급 유지 플레이테스트는 장기 참고이며 이번 완료 조건이나 선행 검사가 아니다.

새 검사는 아직 구현·실행하지 않았다. 현재 Run-Tests는 그래픽 없는 논리/연결 검사이고 Run-Demo/RenderValidation은 고정 해상도이므로, 새 렌더 조합과 두 프로세스 저장/복원에는 기존 도구의 작은 확장이 필요하다. 자동 검사·실제 Player·PNG 정적 확인·사람 조작을 각각 판정한다.

## 검증 층

| 종류 | 목적 | 실행 주체 |
|---|---|---|
| Edit Mode | 화면 없이 초기 상태·자원·규칙 확인 | 환경 구성 후 에이전트 자동 실행 가능 |
| Play Mode | Unity 장면·입력·표시·수명 연결 | CLI 테스트, 실제 렌더 이미지 정적 검토는 별도 |
| Windows 실행 파일 | 에디터 밖 시작과 기능 확인 | CLI 빌드·실행과 상태/종료 증거, 사람 조작은 별도 |
| 실제 플레이 | 이해도·조작 부담·재미 | 사람의 플레이와 피드백 필요 |

Edit Mode는 Unity 실행기를 사용하며 Unity 없는 독립 테스트가 아니다. 배치 종료 코드만으로 성공 처리하지 않는다. 결과 XML의 실행 개수·실패·로그를 확인하고 테스트 0개를 실패로 취급한다. GUI 없는 성공은 렌더링 확인이 아니다.

## Computer Use 없이 실행하는 원칙

이후 UI 자동화는 사용하지 않는다. 기존 0-A의 UI 관찰 기록은 당시 실제 수행한 과거 증거로 보존하며 새 방식으로 다시 수행했다고 바꾸지 않는다.

- Unity 명령줄과 테스트·Editor 스크립트를 활용한다. Edit Mode 실행기는 Tools/Run-Tests.ps1에 구현했다. Play Mode 자동 실행은 E2 범위다.
- 0-E1은 B와 병렬 작성하되 실제 B 검사를 실행하기 전 완료로 처리하지 않는다. 테스트 0개, 실패, 예상 검사 누락, XML 누락, 타임아웃을 성공으로 취급하지 않는다.
- 생성 시 격리(T0-B2)만으로 진행 후 독립성을 입증하지 않는다. 기존 B2의 진행 검사는 T0-D3로 옮겼다.
- 통합 담당자만 동일 프로젝트 Unity를 실행하며 실행 입력 쓰기를 동결한다. 열린 에디터를 강제 종료하지 않는다. 세부 절차는 [ParallelWork.md](ParallelWork.md)를 따른다.
- 실행별 고유 결과 경로, 입력 파일 해시, 에디터·패키지 기준, 명령, 종료 코드와 테스트 수를 남긴다.
- 그래픽 없는 실행은 렌더링 검증이 아니다. 그래픽 환경에서 실제 생성한 이미지의 정적 검토는 UI 자동화 없이 가능하지만, 조작감·가독성·재미와 동적 표시 전체의 검증을 대체하지 않는다.
- 플레이어 프로세스 생존만으로 0-F를 통과시키지 않는다. 필요한 상태와 재시작·종료 증거가 없으면 미검증이다. 시각·수동 기준이 남은 작업은 부분 검증 상태로 둔다.

공식 참고: [Unity CLI 테스트](https://docs.unity.com/en-us/engine/6000.3/manual/programming-environment/test-framework-introduction/running-tests/run-tests-from-command-line). 정확한 실행 인수는 설치된 Test Framework 버전과 대조한 후 실행기에 반영한다.

## T8 통합 시험

고정 맵에서 정착민 3명과 기획 초기 물자로 시작한다. 거처·조리대·저장·경작과 우선순위를 구성한 뒤 개별 행동을 반복 지시하지 않는다.

초기 식사 소진 이후 두 번의 재배·수확 주기 동안 자체 생산으로 생활해야 한다. 포만도 0, 자원 유실·복제, 영구 작업 정지가 없어야 한다. 저장 복원 후 같은 조건을 만족한다.

통로 차단, 저장 포화, 식재료 부족을 각각 만들고 원인 표시와 해소 후 복귀를 확인한다. 정확한 Tick 수·시나리오 설정·기대 수량은 해당 기능 구현 시 고정한다.

실제 플레이에서는 식량 부족 원인을 화면만 보고 해결 가능한지, 정찰 이전의 운영만으로 반복 조작이 과도하지 않은지 확인한다. 자동 검사 통과가 재미를 입증하지는 않는다.

## 현재 CLI 사용법

PowerShell 7에서 프로젝트 루트를 기준으로 실행한다. 동일 프로젝트 에디터는 먼저 정상 종료한다.

```powershell
pwsh -NoProfile -File Tools/Test-ResultValidation.ps1
pwsh -NoProfile -File Tools/Run-Tests.ps1 -Platform EditMode
pwsh -NoProfile -File Tools/Run-Tests.ps1 -Platform PlayMode
pwsh -NoProfile -File Tools/Run-Demo.ps1 -Action Build -TimeoutSeconds 1200
pwsh -NoProfile -File Tools/Run-Demo.ps1 -Action Smoke
```

Run-Tests.ps1은 고정 에디터 버전을 확인하고 전용 파일 핸들 잠금과 기존 Unity 검사로 중복 실행을 거부한다. 제한 시간 기본값은 600초이며 `-TimeoutSeconds`로 지정한다. 타임아웃/예외에는 이 실행기가 시작한 프로세스만 정리한다. 예상 검사 전체 이름은 Tools/expected-editmode-tests.json(33개), expected-playmode-tests.json(13개)이며 테스트 추가·변경 시 함께 갱신해야 한다.

매 실행의 TestResults/<run-id>/summary.json, XML과 로그, 전후 입력 해시를 확인한다. Unity의 정상적인 에셋 재직렬화라도 입력이 바뀌면 실패한다. 변경 원인을 검토하고 안정화한 뒤 재실행하며 실패 기록을 통과로 바꾸지 않는다. validator 자체 검사는 Unity를 실행하지 않는 합성 자료 검사다.


## 데모 검증 경계

Prepare는 새 장면과 Player 설정을 만드는 의도적 변경 단계다. 이미 제공된 장면이 있으면 반복할 필요가 없으며 검증 전에만 실행한다: `pwsh -NoProfile -File Tools/Run-Demo.ps1 -Action Prepare`.

작업1 기준 EditMode는 초기 상태15개, 시간/초기화6개, 이동12개를 검사했다. 당시 PlayMode13개는 기존 통합5개와 이동·시간·입력8개로 구성되며 실제 Image/Text/RectTransform, 위치·수량·타일 색, 자동 시간과 pause, 반복 Bind/Reset 후 객체 수와 버튼 단일 호출을 검사한다. 테스트 이름 목록에 누락·추가·중복·실패·skip이 있으면 CLI는 실패한다.

Run-Demo는 Prepare/Build/Smoke와 Run-Tests 사이에 동일 runner.lock 독점 핸들을 사용한다. 소유 프로세스가 남아 있으면 거부한다. 종료 후 남은 UnityLockfile은 삭제하지 않고, Unity 프로세스가 없는지 검사한 후 독점 파일 열기가 성공할 때만 Unity가 자체 재열기하도록 한다. 사용자의 에디터를 강제 종료하지 않는다.

Build는 입력 전후 일치를 검사하고 build-provenance.json에 소스와 산출물 SHA256을 기록한다. Smoke는 이를 현재 입력·실행 파일과 대조해 오래된 빌드나 변경된 산출물을 거부한다. 소스·Tools가 바뀌면 다시 빌드해야 한다. Docs 변경은 실행 입력이 아니므로 빌드 해시에 포함하지 않는다. 모든 실행은 고유 TestResults 폴더에 남으며 실패 기록을 덮어쓰지 않는다.

Player smoke는 일반 렌더링을 활성화한 실제 Windows 실행이다. 자동 Tick 진행, 명시 시간 10초→100 Tick, 10회 Reset과 단일 버튼 호출, marker 데이터·객체 수, PNG 저장, 정상 종료를 검사한다. PNG는 종료 후 실제 디코드와 이미지 검토로 보완한다. 사람의 마우스 입력·가독성·일반 종료는 [수동 체크리스트](Demo.md)로 분리한다.

Smoke는 실제 렌더링을 위해 데모 창을 잠시 표시하고 검사 후 종료한다. Editor CLI 프로세스는 숨김 실행한다. 숨긴 Player 창은 렌더 증거로 사용할 수 없다. 최종 render.json은 PNG의 1280×800 크기와 표본 색 수를 검사해 빈 화면을 거부한다. 이는 화면 내용의 의미 검증을 대신하지 않는다.

## 기능 우선 검증 원칙 (2026-11-18)

장기 자급과 수치 조정은 후순위로 둔다. 새 기능마다 정상 진행·취소·실패·복구·저장 복원을 관련 기존 기능과 연결해 검사한다. 고정 수치와 충분한 자원은 재현을 위한 시험 조건이며 제품 밸런스의 증거가 아니다. 자원이 부족해 작업을 보류하는 것은 정상일 수 있지만, 보충 후에도 영구 정지하거나 물자가 유실·복제되면 기능 결함이다.

기본 습격은 명령→공격→피해→종료, 치료·복구는 실제 피해→치료/수리→운영 복귀를 검사한다. 새 전투·부상 상태의 저장/복원 및 Reset도 해당 기능에 포함한다. 에이전트는 CLI 규칙·통합·빌드·Player 검사를 수행하고, 실제 조작감과 상황 이해는 사용자 확인으로 구분한다. 구체적인 시험값과 완료 기준 추천안은 [작업9 상세 계획](Plans/Task9-Raid-Recovery.md)에 정리했다. 실행 결과와 직접 조작 확인 항목은 [기본 습격 검증 기록](Verification/2026-11-18-raid-recovery.md)에 있다.
