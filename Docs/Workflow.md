상세 규칙은 해당 문서 한 곳에 두고 다른 문서에서는 링크한다. 실제 상태와 결과는 Status 및 검증 기록을 기준으로 하며, 예정 기능을 설명한 문장을 구현 증거로 사용하지 않는다.

## 작업 시작

1. Status와 해당 작업의 기획·완료 기준을 읽는다.
2. 실제 파일과 환경을 확인한다. 오래된 기록을 현재 사실로 단정하지 않는다.
3. 이번 기능 범위와 실행 가능한 검증을 알린다.
4. 사용자 지시와 문서가 다르면 최신 지시를 반영한다. 중요한 미정 결정만 1~2개씩 확인한다.

## 변경과 종료

- 사용자 보고는 [AGENTS.md의 공통 보고 원칙과 보고 유형별 규칙](../AGENTS.md)을 따른다. 구현 계획을 전달하기 전에는 아래 점검 절차로 핵심 근거가 본문에 포함되었는지 확인한다. 보고 규칙의 본문은 AGENTS.md에서 관리하고 이 문서는 실행 절차를 다룬다.
- 동작을 바꾸면 관련 기획, 구조 또는 검사 기준을 함께 수정한다.
- 수치 변경에는 이전 값·새 값·이유·검증 결과를 기록한다.
- 설계 대안에는 장단점과 선택 이유를 남긴다. 모든 사소한 구현 선택에 별도 결정 기록을 만들 필요는 없다.
- 검사 결과에는 초기 조건과 관측 수치를 남긴다. 통과하지 못한 완료 기준은 미완료 또는 미검증으로 유지한다.
- Status의 다음 행동을 갱신하고 사용자에게 완료·미완료·미검증을 구분해 보고한다.
- 커밋·외부 게시 금지 지시는 명시적으로 해제될 때까지 유지한다.

## 문서 자체의 확인

아트·화면 조사에는 아래 아트 조사와 시각 보고 절차도 적용한다.

- 상대 링크가 실제 문서로 연결되는지 확인한다.
- 확정·초기 조정값·미정·검증 결과가 섞이지 않았는지 확인한다.
- 코드 파일 경로 예시는 예정임을 표시한다.
- 실행하지 않은 테스트, 미생성 lock 파일, 미확인 설치 버전을 완료로 적지 않는다.

## 보고 전 점검

설명 기조와 보고 유형별 기준은 [AGENTS.md](../AGENTS.md)를 따른다. 아래는 답변에 그대로 나열할 목차가 아니라 작성 후 확인할 기준이다.

1. 첫 문단만 읽어도 무엇을 하려는지와 권장 방향을 알 수 있는가? 배경이나 기술 세부사항이 핵심보다 앞서지 않았는가?
2. 중요한 선택 바로 뒤에 현재 구조에 근거한 이유와 의미 있는 대안의 차이가 있는가? 세부 설명이 그 선택을 뒷받침하는가?
3. 동작 흐름 → 필요한 변경 → 검증이 같은 목표로 이어지는가? 중요하지 않은 구현 선택까지 같은 비중으로 펼치지 않았는가?
4. 확인한 코드·추론·제안, 검사 계획·실행 결과를 구분했는가? 핵심 이유나 중요한 실패·미검증을 짧게 쓰려는 이유로 빼지 않았는가?
5. 여러 내용을 다루는 구현 계획을 번호 있는 짧은 소제목으로 나눴는가? 핵심 설계·동작 흐름·구체적인 구현 작업·검증 계획·최종 요약을 기본으로, 단순한 작업은 필요한 만큼 합쳤는가? 긴 강조 문장을 제목 대신 쓰거나 목차만 채우는 내용·의무적인 후속 질문을 추가하지 않았는가?

## 시각 자료를 사용하는 경우

- 비교가 필요한 주장에 맞는 자료를 선택한다. 같은 조건에서 차이를 보여주고, 자료 가까이에 관찰 지점과 그 차이가 중요한 이유를 설명한다. 단순 설명에는 비교 그림을 강제하지 않는다.
- 실제 오류를 확인하지 않았다면 가상 사례라고 표시한다. 원본 참고·개념도·제작안·실제 실행 화면과 검증 수준을 구분한다.
- 표현 방식의 실제 표시 지원과 별도 파일 생성 승인을 확인한다. 그림이 필요하다는 판단만으로 로컬 파일·웹페이지 생성 승인이 생기지 않는다. 지원되지 않는 표현을 성공한 것처럼 보고하지 않는다.
- 아트의 시점 차이는 같은 배치의 비교 이미지로 보여줄 수 있다. 정착민·침대·나무의 시점이 섞인 경우와 맞춘 경우를 비교하고, 바닥 접점이나 상대 크기를 어디서 읽기 어려운지 표시한다. 단지 원본을 나열하거나 “통일감 향상”이라고 쓰는 것으로 끝내지 않는다. 자료 제작은 승인된 범위에서 진행한다.

## 아트 조사와 시각 보고 절차

2026-11-17 사용자 요청으로 추가. [AGENTS.md](../AGENTS.md)의 핵심 방향과 선택 이유를 먼저 설명하는 기조를 따른다. 아래 항목은 조사·제작 시 점검할 내용이며 보고 본문에 전부 나열할 목차가 아니다. 별도 시각화 파일 제작은 승인된 범위에서 수행한다.

1. 다음 계획·완료 기준·현재 종류/상태를 읽고 필요한 아트를 기능별로 정리한다. 장기 기능을 현재 필요 목록으로 부풀리지 않는다.
2. 프로젝트와 관련 설치·다운로드 폴더에서 실제 파일을 찾는다. 검색 범위, 정확한 경로, 형식, 해상도, 출처와 사용 조건 확인 상태를 남긴다. 파일 이름만 찾은 것과 정상 이미지를 확인한 것을 구분한다.
3. 대상별로 시점, 실루엣, 팔레트, 외곽선, 화면 크기, 바닥 접점, 방향·성장·작업 변형, UI/수량의 별도 표시, 임시→최종 교체 방법을 제안한다. 이미지 크기를 점유·통행 규칙으로 사용하지 않는다.
4. 실제 참고 이미지와 제작 규격 설명 그림을 제공한다. 확대·축소, 대상별 비교, 표시 크기/점유 차이처럼 조작이 이해에 도움이 될 때 인터랙티브 자료를 사용한다. 원본 참고/개념도/실제 게임 캡처를 명확히 표시한다.
5. 작은 기준 샘플을 먼저 제작하고 실제 게임 화면에서 확인한 뒤 전체 제작으로 확대한다. 이번에 수행한 파일/정적/렌더 검사와 향후 Unity/사람 검증을 구분한다. 보고 자료의 버튼이 작동해도 제품 구현 완료가 아니다.
6. 본문에서 확인 결과·프로젝트 적용안·이유·다음 순서를 직접 설명하고 상세 문서는 보조 링크로 연결한다. 로컬 참고 자료는 외부 게시 승인을 뜻하지 않으며 커밋도 별도 승인이다.

## 병렬 작업과 검토 절차

공통 계약·파일 소유권을 정하고 독립 구현만 병렬화한다. 통합 담당자가 공유 설정·최종 문서·상태를 반영하며 Unity 실행 전 입력 쓰기를 동결한다. 자세한 절차는 [ParallelWork.md](ParallelWork.md)를 따른다.

여러 에이전트를 사용한 검토는 역할별 독립 의견을 받은 뒤 핵심 반론을 교차 전달하고, 채택·보완·제외 이유를 Docs/Reviews에 기록한다. 검토 합의를 구현 성공이나 성능 개선의 증거로 사용하지 않는다. 작업 종료 시 문서 링크와 상태 일관성도 확인한다.

Computer Use 및 다른 UI 자동화는 사용하지 않는다. CLI 검증과 실제 렌더 이미지 검토, 사용자 수동 검증을 구분한다.

## 현재 Git 승인 범위

2026-11-19에는 누적 변경을 기능별로 커밋하고 main에 통합해 origin으로 푸시하도록 승인받았다. 이후 변경의 커밋과 게시는 별도 승인을 받는다.

### 2026-11-15 당시 승인

2026-11-15 최초 기준 커밋에 이어 검증된 이동·생활·소집·점유와 관련 문서의 통합 기준 커밋 1회를 승인받았다. 이후 커밋은 변경과 검증 결과를 정리한 뒤 다시 승인받는다. 공유 작업 폴더를 유지하고 원격 연결·push는 하지 않는다. 과거 검증 문서의 “Git 미초기화” 기록은 당시 상태이므로 소급 수정하지 않는다.

## 기능별3커밋 승인 (2026-11-15)

사용자가 채집·운반·저장, 표시 개선, 정지 명령 즉시 적용/저장 도구 해제의3개 커밋을 승인했다. 각 중간 상태를 검증하고 최종 제품 입력이 시작 시 보존본과 일치하는지 확인한 뒤 저장한다. 이번 승인 이후 추가 커밋은 다시 승인받으며 원격 연결·push는 하지 않는다. [검증 기록](Verification/2026-11-15-feature-commits.md)을 따른다.

## 여러 세션에 걸친 인계

[다중 세션 계획](Plans/MultiSessionRoadmap.md)의 작업 카드로 기준 커밋/계약 버전/허용 파일/완료 기준/검사 결과/다음 행동을 기록한다. 새 세션은 대화 기억 대신 이 카드와 현재 파일을 읽는다. 전체 Status·계약·공유 파일은 S0, 기능별 계획과 전용 파일은 해당 세션이 관리한다. 변경 요청은 영향과 회귀 기준을 함께 제시하고, 다른 소유자의 파일을 임의 수정하지 않는다. 작업 공간을 분리하더라도 의미상 충돌을 검토하고 한 결과 단위씩 통합한다. 계획 요청은 구현·세션 생성·커밋 승인이 아니다.


## 현재 세션 지시서 우선순위

[현재 3세션 계획](Plans/SettlementFiveFeatures.md)과 연결된 S0/SA/SB 지시서를 새 세션의 출발점으로 사용한다. 전체 로드맵 지시보다 현재 한정 범위가 우선한다. 역할 교체가 파일 소유권 이전을 뜻하지 않는다. 통합 담당이 변경 단위/기간/소유자를 기록해야 다른 담당이 수정할 수 있다. 각 세션은 자기 지시서의 작업 카드에 결과를 남기고 전체 Status는 S0만 수정한다.

## G0 인계 버전 (2026-11-15)

현재 기능 인계는 `settlement-five-v2`와 [G0 준비 확정서](Plans/G0-Preparation.md)를 기준으로 한다. 작업 카드에는 실제 제품 기준과 문서 manifest를 함께 적는다. G0-D 명세 완료를 API 구현/컴파일 통과로 기록하지 않는다. 실제 연결 구현·회귀 G0-C가 통과해야 SA/SB에 제품 작성을 배정한다.
