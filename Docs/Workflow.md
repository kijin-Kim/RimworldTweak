상세 규칙은 해당 문서 한 곳에 두고 다른 문서에서는 링크한다. 실제 상태와 결과는 Status 및 검증 기록을 기준으로 하며, 예정 기능을 설명한 문장을 구현 증거로 사용하지 않는다.

## 작업 시작

1. Status와 해당 작업의 기획·완료 기준을 읽는다.
2. 실제 파일과 환경을 확인한다. 오래된 기록을 현재 사실로 단정하지 않는다.
3. 이번 기능 범위와 실행 가능한 검증을 알린다.
4. 사용자 지시와 문서가 다르면 최신 지시를 반영한다. 중요한 미정 결정만 1~2개씩 확인한다.

## 변경과 종료

- 동작을 바꾸면 관련 기획, 구조 또는 검사 기준을 함께 수정한다.
- 수치 변경에는 이전 값·새 값·이유·검증 결과를 기록한다.
- 설계 대안에는 장단점과 선택 이유를 남긴다. 모든 사소한 구현 선택에 별도 결정 기록을 만들 필요는 없다.
- 검사 결과에는 초기 조건과 관측 수치를 남긴다. 통과하지 못한 완료 기준은 미완료 또는 미검증으로 유지한다.
- Status의 다음 행동을 갱신하고 사용자에게 완료·미완료·미검증을 구분해 보고한다.
- 커밋·외부 게시 금지 지시는 명시적으로 해제될 때까지 유지한다.

## 문서 자체의 확인

- 상대 링크가 실제 문서로 연결되는지 확인한다.
- 확정·초기 조정값·미정·검증 결과가 섞이지 않았는지 확인한다.
- 코드 파일 경로 예시는 예정임을 표시한다.
- 실행하지 않은 테스트, 미생성 lock 파일, 미확인 설치 버전을 완료로 적지 않는다.

## 병렬 작업과 검토

공통 계약·파일 소유권을 정하고 독립 구현만 병렬화한다. 통합 담당자가 공유 설정·최종 문서·상태를 반영하며 Unity 실행 전 입력 쓰기를 동결한다. 자세한 절차는 [ParallelWork.md](ParallelWork.md)를 따른다.

여러 에이전트를 사용한 검토는 역할별 독립 의견을 받은 뒤 핵심 반론을 교차 전달하고, 채택·보완·제외 이유를 Docs/Reviews에 기록한다. 검토 합의를 구현 성공이나 성능 개선의 증거로 사용하지 않는다. 작업 종료 시 문서 링크와 상태 일관성도 확인한다.

Computer Use 및 다른 UI 자동화는 사용하지 않는다. CLI 검증과 실제 렌더 이미지 검토, 사용자 수동 검증을 구분한다.

## 현재 Git 승인 범위

2026-11-15 최초 기준 커밋에 이어 검증된 이동·생활·소집·점유와 관련 문서의 통합 기준 커밋 1회를 승인받았다. 이후 커밋은 변경과 검증 결과를 정리한 뒤 다시 승인받는다. 공유 작업 폴더를 유지하고 원격 연결·push는 하지 않는다. 과거 검증 문서의 “Git 미초기화” 기록은 당시 상태이므로 소급 수정하지 않는다.

## 기능별3커밋 승인 (2026-11-15)

사용자가 채집·운반·저장, 표시 개선, 정지 명령 즉시 적용/저장 도구 해제의3개 커밋을 승인했다. 각 중간 상태를 검증하고 최종 제품 입력이 시작 시 보존본과 일치하는지 확인한 뒤 저장한다. 이번 승인 이후 추가 커밋은 다시 승인받으며 원격 연결·push는 하지 않는다. [검증 기록](Verification/2026-11-15-feature-commits.md)을 따른다.

## 여러 세션에 걸친 인계

[다중 세션 계획](Plans/MultiSessionRoadmap.md)의 작업 카드로 기준 커밋/계약 버전/허용 파일/완료 기준/검사 결과/다음 행동을 기록한다. 새 세션은 대화 기억 대신 이 카드와 현재 파일을 읽는다. 전체 Status·계약·공유 파일은 S0, 기능별 계획과 전용 파일은 해당 세션이 관리한다. 변경 요청은 영향과 회귀 기준을 함께 제시하고, 다른 소유자의 파일을 임의 수정하지 않는다. 작업 공간을 분리하더라도 의미상 충돌을 검토하고 한 결과 단위씩 통합한다. 계획 요청은 구현·세션 생성·커밋 승인이 아니다.


## 현재 세션 지시서 우선순위

[현재 3세션 계획](Plans/SettlementFiveFeatures.md)과 연결된 S0/SA/SB 지시서를 새 세션의 출발점으로 사용한다. 전체 로드맵 지시보다 현재 한정 범위가 우선한다. 역할 교체가 파일 소유권 이전을 뜻하지 않는다. 통합 담당이 변경 단위/기간/소유자를 기록해야 다른 담당이 수정할 수 있다. 각 세션은 자기 지시서의 작업 카드에 결과를 남기고 전체 Status는 S0만 수정한다.

## G0 인계 버전 (2026-11-15)

현재 기능 인계는 `settlement-five-v2`와 [G0 준비 확정서](Plans/G0-Preparation.md)를 기준으로 한다. 작업 카드에는 실제 제품 기준과 문서 manifest를 함께 적는다. G0-D 명세 완료를 API 구현/컴파일 통과로 기록하지 않는다. 실제 연결 구현·회귀 G0-C가 통과해야 SA/SB에 제품 작성을 배정한다.
