# 병렬 작업 검토와 토의 기록

날짜: 2026-11-15. 구현·실행 시험이 아닌 문서 및 현재 파일 상태에 대한 설계 검토다.

## 참여와 방법

- dependencies: 기능 의존성과 0-B~0-F 및 작업 1~8의 병렬 가능성 검토.
- verification: Computer Use 없는 검사, CLI 실행과 증거·완료 기준 검토.
- ownership: 공유 작업공간의 파일 충돌, 소유권과 통합 절차 검토.
- root: 초안 통합, 교차 질문 전달, 최종 문서 반영.

세 에이전트는 읽기만 수행했다. 각 초안을 받은 뒤 B의 Tick 의존성, C/D 재시작 배선, Unity 동시 실행과 입력 동결을 교차 논의했고 각 검토자가 최종 합의 의견을 반환했다. 문서 수정은 root 한 명이 수행했다.

## 쟁점과 최종 반영

| 초기안/질문 | 검토·반론 | 최종 반영 |
|---|---|---|
| B~F를 모두 동시 시작할 수 있는가 | 데이터·시간·장면 연결이 서로 의존 | 계약 → B+E1 → C+D+검사 작성 → 통합 → F |
| E는 마지막에 만들면 되는가 | 초기 B 검사에 실행·결과 판정 기반 필요 | E1 앞당김, 실제 검사 없이 완료 금지; E2로 통합 마무리 |
| B에서 한 월드만 진행해 독립성 검사 | Tick은 D 기능이므로 순환 의존 | B2는 입력 변경 비전파, 기존 진행 검사는 D3로 이동 |
| C와 D는 서로 완전히 독립인가 | Reset 뒤 표시·구독 정리는 공유 경계 | 코드는 분리 작성, Scene/Bootstrap과 재시작 재연결은 단일 통합 |
| D는 Runtime만 수정하면 되는가 | Simulation의 Tick 상태 변경도 필요 | B 종료 후 해당 파일 소유권 인계 |
| root가 D와 통합자를 겸하면 과부하인가 | 초기화·장면 배선의 충돌을 줄일 수 있음 | 작은 현재 범위에서는 겸임 권장; 4명 상시 가동 강제하지 않음 |
| 테스트·빌드를 동시에 실행해 시간을 줄일 수 있는가 | 동일 프로젝트·Library·실행 입력이 공유됨 | 한 명이 단일 큐 실행, 소스·설정·Tools·시나리오까지 쓰기 동결 |
| UI 자동화를 없애면 화면 기준도 제외하는가 | headless 통과는 렌더링 증거가 아님 | 실제 렌더 이미지 정적 검토/사용자 수동 확인 분리, 미검증 표시 유지 |
| F는 플레이어가 켜지면 통과인가 | 기능 초기화·재시작 성공을 알 수 없음 | 예상 상태·재시작·정상 종료 증거 요구 |

## 채택하지 않은 접근

- 전 작업 일괄 병렬화: 예약·소비·이동·저장 상태 의존을 무시하므로 제외.
- 초기부터 worktree/프로젝트 복제 기반 병렬 실행: Git 미초기화와 현재 규모를 고려해 도입하지 않음.
- 계약을 범용 프레임워크로 확장: 초기 기능에 필요한 최소 접점만 고정.
- Computer Use를 다른 UI 자동화로 대체하거나 화면 완료 기준 삭제: 사용자 의도와 검증 원칙에 맞지 않음.

## 결과와 한계

세 검토자는 코드 작성 병렬·Unity 실행 직렬, B/E1 조기 병렬, C/D 계약 후 분리와 통합 검증에 동의했다. 상세 담당 범위와 순서는 [ParallelWork.md](../ParallelWork.md)에 반영했다.

문서 반영 후 verification이 최종 교차 점검했고 모순·검증 과장은 발견하지 않았다. 추가 의견에 따라 P3 기능 검사 통과 후 시각·수동 확인만 남은 경우 P4 CLI 검사를 계속할 수 있되 전체 완료 표시는 보류하도록 명확히 했다.

검토는 일정 단축·실행기 안정성·성능을 측정한 것이 아니다. 후속 구현과 실제 검사 전까지 해당 기능은 미착수·미검증으로 유지한다. 기존 0-A의 완료 기록은 바꾸지 않았다.
