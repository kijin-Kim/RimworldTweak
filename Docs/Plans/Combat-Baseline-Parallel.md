# 기본 전투의 기능 분리와 병렬 작업 계획

작성일: 2026-11-17. 상태: 계획 정리 완료 대상, 제품 구현·배정 실행·Unity 검증은 미실행. [기본 전투 우선 계획](Combat-Baseline-Incremental.md)의 범위를 유지하면서 B1~B5를 기능 의존성과 파일 소유권에 맞게 분해한다. 기본 전투 확인 후 확장을 하나씩 선택하는 원칙은 바꾸지 않는다.

## 1. 핵심 설계: 기능은 분리하고 같은 상태의 변경은 한곳에서

기존 B4에는 방어구, 부상, 구조, 치료, 회복이 함께 들어 있었다. 이것은 플레이 결과를 묶은 표현이지 독립 구현 단위가 아니다. B1~B5는 플레이 수락 기준으로 남기고 실제 작업 배정은 이 문서의 기능 단위를 따른다.

### 건강·부상·방어구·의료의 경계

| 기능 | 맡는 일 | 맡지 않는 일 | 상태 변경의 주체 |
|---|---|---|---|
| 건강 HP | 현재 부상들로부터 생존·무력화·행동 가능 여부를 판단하고 건강 변경을 검증·적용 | 사격 명중, 방어구 감소, 구조자의 경로, 치료 작업 진행 | HealthRules가 HealthState를 변경하는 유일한 경로. 이름은 제안 |
| 부상 IN | 방어구 처리 뒤 남은 피해를 신규 부상/악화로 변환하고 부상 이력을 생성 | 방어구를 재계산하거나 치료자를 이동시킴 | InjuryRules가 변경 요청을 만들고 HealthRules가 적용 |
| 방어구 AR | 공격 정보와 착용 장비로 차단·감소 후 잔여 피해를 계산 | 부상 생성, 체력 직접 변경, 치료 | 순수 판정 결과만 반환. 건강 상태를 소유하지 않음 |
| 구조 RS | 무력화된 대상을 점유하고 이동·내려놓기로 안전한 장소에 옮김 | 부상 제거, 건강 회복 | RescueState는 구조 행동만 보관. 실제 위치·점유는 통합 담당의 기존 World 연결로 변경 |
| 치료 MD | 치료자가 대상에게 접근하고 작업을 수행해 치료 처치 결과를 제출 | 구조를 반드시 선행시키거나 즉시 완치 처리 | TreatmentState는 작업 진행, 처치 여부는 HealthRules를 통해 부상에 기록 |
| 회복 RC | 시간·치료 여부 등에 따라 부상 상태가 호전되는 규칙 | 치료자 이동과 예약, 죽은 대상 부활 | RecoveryRules가 변화량을 만들고 HealthRules가 적용 |

건강·부상·회복은 기능과 검사는 나누되 같은 담당 SB가 작성한다. 여러 담당이 별도의 HP/부상 목록/회복 값을 관리하면 어느 값이 진짜 상태인지 충돌하기 때문이다. 건강은 부상 목록을 기준으로 상태를 계산하는 최소 모델을 제안하며, 별도 수치가 필요하면 같은 변경 경로에서만 갱신한다. 최종 수식·치료 시간·무력화 임계값은 K에서 작은 시험값으로 정하고 제품 밸런스로 확정하지 않는다.

치료와 회복을 구분하면 '처치는 끝났지만 아직 이동할 수 없는 상태'를 표현할 수 있다. 현장 치료를 허용하는 제안에서는 구조와 치료 사이에 필수 의존이 없다. 안전한 위치로 옮기는 구조와 현장에서 처치하는 치료를 병렬로 작성할 수 있다. 치료 장소 제한을 나중에 선택하면 이 의존을 다시 평가한다.

첫 범위는 단순 방어구, 최소 부상·무력화·사망과 회복이다. 장기별 질병·수술·감염·다층 관통·의약품 생산은 추가하지 않는다. 초기 치료는 별도 소모품 없이 작동하는 안으로 시험하고 소비를 추가할 때 물자 예약을 연결한다. 장비는 시나리오의 초기 무기/방어구 설정부터 제공하고 전투 중 장비 교체 UI·생산은 필수가 아니다.

### 현재 소스에서 확인한 공유 접점

- WorldState.QueueMove / SetDrafted / Step: 명령·소집·시간 처리의 중심이다. 공격·의료·무력화 연결 때문에 여러 담당이 동시에 편집하지 않는다.
- ColonistState: 위치·행동·소집과 작업 운반 CargoKind/CargoAmount를 가진다. 구조 대상이나 장비를 기존 물자 운반 값으로 덮어쓰지 않는다.
- ConstructionRules.BlocksMovement: 벽과 조리대를 막는 통행 규칙이다. SP의 사격 차단·부분 엄폐 판정과 별개다.
- InteractionClaim: OwnerId와 ActionId로 점유한다. 의료에서도 기존 점유와 충돌하지 않도록 S0 연결로 통일한다. 환자·침대에 별도의 중복 소유자를 만들지 않는다.
- SaveData / SaveValidation / WorldState.Save / EntitySaveState: 저장 헤더·상태·복원 검증의 공유 지점이다. 현재 버전 검사는 구체 버전값을 검사하므로 새 상태가 자동 호환된다고 가정하지 않는다.
- SimulationRunner, SettlementShell, WorldMapInput/View: 기존 입력과 표시의 연결 지점이다. 담당별 전용 패널은 만들 수 있지만 등록·배치는 S0이 한다.

이것은 지정 파일의 소스 확인 결과이며 게임 실행 증거가 아니다. 여기서 제안하는 전투·건강 클래스와 계약은 현재 구현된 API가 아니다. 기존 생활·건설/UI 담당의 작성이 진행 중이면 S0이 착수 전 최신 상태와 소유권 인계를 확인해야 한다.

## 2. 처리 흐름과 개발 의존성

### 실제 게임의 처리 흐름 제안

```text
명령/적 판단 → 조준·발사 → 사선·명중 → 방어구 → 잔여 피해 → 부상 생성
                                                                  ↓
                                                         건강/행동 가능 상태
                                                                  ↓
                                              행동 중단·예약 해제·전투 결과

건강/무력화 → 구조 → 위치 변경
부상 + 치료 명령 → 치료 작업 → 처치 기록 → 시간에 따른 회복 → 건강 재평가
```

이 화살표는 데이터가 흐르는 순서다. 방어구 개발이 공격 구현 완료를 기다려야 한다는 뜻은 아니다. 공격 입력 자료가 정해지면 방어구는 예시 입력으로 독립 구현할 수 있고, 건강도 예시 부상을 적용하며 독립 구현할 수 있다. 다만 예시 입력 시험이 실제 공격 연결을 증명하지는 않는다.

### 기능 의존성 표

선행 열은 **실제 제공 기능을 이용한 규칙 검증의 선행**이다. K의 입력·출력 정의만으로 초안 작성/시험 데이터 준비를 앞당길 수 있지만 선행 구현과 연결하지 않은 기능을 통합 완료로 표시하지 않는다. K는 기본 전투용 최소 공통 접점이며 전투 자체의 완료 항목이 아니다.

| ID | 기능 | 선행 | 담당 | 규칙 단위 결과와 수락 근거 |
|---|---|---|---|---|
| K | 공통 연결·명령·상태 계약 | - | S0 | ID/진영·위치 조회, 행동 취소, 공격/피해/건강 변경 자료, 점유·저장·처리 순서·UI 조회를 정의하고 현재 이동·취소 연결 확인 |
| SP | 사선·명중·방향 엄폐 | K | SA | 사거리·완전 차단·부분 엄폐·방향·사수 능력에 따른 판정. 같은 입력의 판정과 UI 설명 일치 |
| EQ | 무기·방어구 설정과 착용 상태 | K | SC | 원거리 2종/근접 1종과 단순 방어구, 유효한 초기 착용 상태. 명령이나 피해 적용을 실행하지 않음 |
| HP | 건강 상태와 변경 경로 | K | SB | 생존·무력화·행동 가능 조회와 상태 변경 검증. 죽은 대상의 치료/회복 거부 |
| AR | 방어구 피해 판정 | EQ | SC | 장비·공격 입력에서 잔여 피해 반환. 감소가 중복 적용되지 않고 음수 피해를 만들지 않음 |
| IN | 부상 생성·악화·이력 | HP | SB | 잔여 피해로 부상 생성, 완전 차단 피해에서는 신규 부상 없음, 신규 부상 이력 보존 |
| AT | 지휘·원거리/근접 공격 진행 | SP,EQ,HP | SA | 조준·발사·회복, 표적·사격 보류, 접촉 공격, 취소. 유효 발사/타격 결과를 반환. 실제 부상 연결 수락은 G2에서 AR/IN까지 필요 |
| RC | 시간에 따른 회복 | IN | SB | 부상과 처치 상태에 따른 회복, 과회복·사망 복구 방지. 실제 치료 명령 연결은 G2에서 검증 |
| RS | 구조·이송·중단 | HP | SC | 무력화 대상·목적지 점유, 이동·내려놓기, 구조자 중단/사망·경로 차단 시 안전한 정리. 치료는 선행 아님 |
| MD | 접근·치료 작업·처치 | IN | SC | 치료 가능 부상 선택, 대상 점유·작업·중단, 처치 요청을 건강 경로에 전달. 구조와 회복 완료는 선행 아님 |
| AI | 기본 적 행동 | SP,EQ,HP,AT | SA | 접근·엄폐 선택·공격·철수 요청. 플레이어와 같은 공격 명령/판정을 사용하고 별도 피해 공식 없음 |
| BT | 작은 방어전·결과 | AI,HP,IN | S0 | 고정 적 구성·보호 목표·시작/종료·신규 부상 이력. 규칙 단위 종료와 전체 구조/복구 경험의 완료는 구분 |

선행에 K가 반복되지 않은 항목은 선행 기능을 통해 K를 이어받는다. 기본 전투 전체 수락 G3에는 위 모든 기능과 실제 구조→치료→회복→작업 복귀, 저장·UI가 필요하다. AT 단독 통과나 BT의 승패 판정만으로 전체 전투 완료를 선언하지 않는다.

진행이 막히기 쉬운 경로는 K → HP → IN → MD/RC의 건강·의료 연결과 K → SP/EQ/HP → AT → AI → BT의 실제 교전이다. AR은 비교적 앞에서 병렬로 준비할 수 있지만 최종 피해 연결 G2에서 반드시 합쳐야 한다. 두 경로의 작성이 끝나도 S0의 저장·UI·취소 연결과 직렬 검사가 남으므로 담당 수만 늘려 완료 시점이 비례해서 빨라진다고 가정하지 않는다. 기간은 아직 산정하지 않았다.

### 불필요한 의존을 제거한 이유

- AR은 HP·IN·MD를 기다리지 않는다. 방어구 결과는 부상 종류와 독립적인 잔여 피해다.
- IN은 AT·AR의 구현을 기다리지 않는다. 정해진 잔여 피해 입력으로 먼저 만든 뒤 G2에서 실제 경로를 연결한다.
- RC는 MD의 작업 구현을 기다리지 않는다. 처치 여부가 있는 부상 자료로 먼저 검사하고 실제 처치는 G2에서 연결한다.
- RS는 MD·RC를 기다리지 않는다. 건강 조회와 위치/점유 접점만 필요하다.
- MD는 RS를 기다리지 않는다. 현장 치료가 가능한 기본안으로 환자를 이동시키지 않고도 검사한다.
- 무기/방어구 설정 EQ와 사선 SP는 공통 자료만 공유한다. SP는 EQ 파일을 직접 고치지 않고 전달된 무기 수치를 사용한다.
- 방어 기본 경험에 제압·탄약·Fog of War를 선행시키지 않는다. 이들 추가는 기본 전투 확인 뒤 별도 선택이다.

## 3. 공통 계약, 소유권과 병렬 배치

### 착수 전 고정할 최소 계약 K

한 기능의 상태를 여러 사람이 직접 쓰지 않게 다음 자료와 동작을 정한다. 아래 이름은 후보이며 아직 API 서명을 확정하거나 제품 파일을 만든 것은 아니다.

| 접점 | 내용과 불변 조건 | 제공/변경 책임 |
|---|---|---|
| 전투 주체 조회 | ID·진영·위치·소집·행동 가능 상태, 플레이어가 적을 명령하지 못함 | S0가 현재 World에 연결, HP의 건강 조회를 사용 |
| AttackResult / DamageInput | 원인/대상 ID, 공격 종류·기본 피해, 발사 Tick과 식별, 같은 공격 이중 적용 방지 | 공통 형식 S0, 생성 SA, 방어 판정 SC |
| DamageResult / HealthChange | 방어 후 잔여 피해와 부상/처치/회복 변경 요청. AR에서 체력 변경 금지 | 형식 S0, 규칙 SB가 유효성 검사·적용 |
| 건강 조회와 이력 | 상태·행동 제한·읽기 전용 부상·신규 부상 기록. HP/IN/RC 모두 같은 HealthRules 경로 | SB가 소유. 공격·의료·AI는 조회/요청만 |
| 이동·환자·침대 점유 | 환자 ID·행동 ID와 실제 장소, 중단 시 정리, 운반 중 중복 위치 금지 | 공통 World/기존 점유 연결 S0, 구조/치료 진행 SC |
| 저장 자료 | 공격 단계·건강/부상·착용·의료 진행과 점유 관계, 난수 진행 상태, 임무 이력 | 전용 자료/직렬화 제안은 기능 담당, 루트·버전/마이그레이션·복원 조합 S0 |
| 표시 자료 | 상태와 명령 불가 이유, 조준·엄폐·부상·처치 표시 | 전용 패널 각 담당, 입력/배치/조회 연결 S0 |

건강 수식, 방어구 감소 방식, 명중 시험값, 근접 접촉·충돌, 같은 Tick의 상호 타격, 사망과 처치 완료 충돌은 첫 묶음 시작 전 K의 시험 사례로 고정한다. 값이 미정인 채 각 담당이 서로 다른 기본값을 넣지 않는다. 전체 미래 기획을 확정할 필요는 없다.

추천 Tick 원칙: 명령 취소/이동 반영 → 유효한 공격 결과 수집 → 방어·부상 반영 → 건강 전이와 행동/예약 정리 → 남아 있는 유효 의료 완료/회복 처리 → 임무 결과. 같은 Tick에 이미 유효했던 상호 공격은 한쪽 목록 순서로 지우지 않으며 사망 후 치료를 적용하지 않는다. 회복으로 기존 신규 부상 이력은 지우지 않는다. 정확한 기존 생활/작업 삽입 위치는 S0가 회귀 검사와 함께 확정한다.

### 역할별 파일 소유권 제안

통합 S0 + 독립 기능 3담당 SA/SB/SC를 권장한다. 건강과 부상을 별도 인원으로 늘리기보다 같은 변경 경로를 유지하고, SC가 방어구를 끝낸 뒤 의료 행동으로 이동한다. 세 기능 담당을 확보할 수 없으면 SC 작업을 앞뒤 묶음으로 순차 수행하며 소유권 이전을 기록한다. 인원 수가 기능 수와 같을 필요는 없다.

모든 아래 신규 파일은 **예정 경로**다. 착수 시 실제 충돌 여부를 다시 확인하고 `.meta`도 같은 담당이 소유한다. 전용 파일 이름을 바꾸면 이 표를 먼저 갱신한다.

| 담당 | 독점 작성할 파일/영역 | 수정하지 않을 영역 |
|---|---|---|
| S0 통합 | 기존 WorldState*.cs, ColonistState.cs, ConstructionRules.cs, WorkEntities/LivingEntities, 기존 SaveData·SaveValidation·EntitySaveState·SimulationSession.Save, SimulationRunner*, 기존 Shell/View/WorldMap*, Demo·Scene·Editor·Tools·설정·asmdef·manifest, 전체 상태/결정 문서. 새 Simulation/CombatContracts.cs, WorldState.Combat.cs, WorldState.Medical.cs, BattleScenario.cs, BattleRules.cs, CombatSaveData.cs, Tests/PlayMode/Integration/CombatBaselineIntegrationTests.cs | 작성 중인 SA/SB/SC 전용 파일을 임의 변경하지 않음 |
| SA 공간·공격·적 | 새 Simulation/CombatSpatialRules.cs, AttackState.cs, AttackRules.cs, EnemyCombatRules.cs, Presentation/CombatCommandPanel.cs, CombatOverlay.cs, Tests/EditMode/Simulation/CombatSpatialTests.cs, AttackRulesTests.cs, EnemyCombatTests.cs | 건강·장비·의료 상태 직접 수정, WorldState/Runner/Shell 연결 |
| SB 건강·부상·회복 | 새 Simulation/HealthState.cs, HealthRules.cs, InjuryRules.cs, RecoveryRules.cs, HealthSaveData.cs, Presentation/HealthPanel.cs, Tests/EditMode/Simulation/HealthRulesTests.cs, InjuryRulesTests.cs, RecoveryRulesTests.cs | 장비/피해 감소·치료 작업 진행·공유 저장 헤더 직접 수정 |
| SC 장비·방어구·의료 행동 | 새 Simulation/EquipmentState.cs, EquipmentRules.cs, ArmorRules.cs, RescueState.cs, RescueRules.cs, TreatmentState.cs, TreatmentRules.cs, MedicalSaveData.cs, Presentation/EquipmentPanel.cs, MedicalCommandPanel.cs, Tests/EditMode/Simulation/EquipmentRulesTests.cs, ArmorRulesTests.cs, RescueRulesTests.cs, TreatmentRulesTests.cs | 건강 원본 직접 변경, 기존 침대/생활 점유·WorldState·공유 UI 직접 수정 |

경로에서 생략된 앞부분은 Assets/Game/다. 공격·장비 저장 자료는 S0의 CombatSaveData에 슬롯을 등록하고, 기능 담당은 필드/검증 규칙과 왕복 사례를 제공한다. 건강/의료 전용 저장 자료는 담당이 작성하지만 저장 루트에 연결하고 상태를 실제로 복원하는 것은 S0다. 전투 기록은 임무에 필요한 항목만 보관하고 범용 이벤트 프레임워크를 선행 구축하지 않는다.

### 실행 묶음과 통합 문턱

| 묶음 | SA | SB | SC | S0 및 다음 묶음 진입 조건 |
|---|---|---|---|---|
| 준비 P0 | 입력·판정 사례 검토 | 건강·변경 경로 검토 | 장비·의료 점유 사례 검토 | K와 파일 소유권 고정, 현재 코드 인계. 구현 승인 이후에만 최소 접점 구현 및 G0 검사 |
| P1 기반 병렬 | SP 사선·엄폐 | HP 건강 → IN 부상 | EQ 장비 → AR 방어구 | 기존 이동/소집·점유·저장 연결 준비. 모두 인계 후 동결하고 G1 직렬 통합 검사 |
| P2 행동 병렬 | AT 지휘·원거리/근접 공격 | RC 회복 | RS 구조, MD 치료를 같은 담당 안에서 순차 작성 | 실제 공격→방어구→부상과 의료 명령→처치→회복, 입력·전용 패널·저장을 연결. G2 통과 후 진행 |

P1에서 HP가 먼저 제공돼도 SB의 IN을 건너뛰어 전체 건강 완료로 처리하지 않는다. P2의 RS와 MD는 기술적으로 독립이지만 같은 SC가 맡으므로 실행 일정에서는 순차다. P3의 보완 작업은 새 기능 범위가 아니며 앞선 결과의 실제 연결 확인이다.

- G0: 공통 형식과 실제 현재 이동·취소·점유 연결의 최소 컴파일/회귀 검사. 서명만 있는 스텁이나 문서 합의를 구현 검증으로 취급하지 않는다. 게임 기능 완료 아님.
- G1: 실제 SP/EQ/AR/HP/IN 규칙과 S0 연결을 검사. 주입 공격 자료로 피해→부상까지 확인하되 아직 플레이 사격 결과가 아님을 표시. 기존 생활과 새 건강 상태의 저장 왕복 포함.
- G2: 실제 플레이 명령으로 발사→명중→방어구→부상을 거치고, 구조/현장 치료/회복 경로를 실제 World에서 확인. 새 상태 전부 저장·복원. 기본 적 AI 없는 제어된 교전 시험이며 한 판 전체 완료 아님.
- G3: 고정 방어전에서 실제 AI와 시작/종료·치료/복귀·두 번째 전투·기존 저장 호환을 검증. 자동 검사, 실제 렌더, 사용자 직접 플레이 증거를 따로 기록. 여기까지 충족해야 기본 전투 전체 완료.

공유 작업 공간에서 쓰기를 병렬로 진행하더라도 같은 프로젝트의 Unity import·컴파일·EditMode/PlayMode·빌드는 S0 한 명이 직렬 실행한다. 검사 전에 모든 작성자가 소스·설정·에셋·검사·시나리오 쓰기를 중지하고 인계 상태를 고정한다. 검사 실패 중에는 원인을 고쳐야 할 소유자에게만 수정 구간을 열고 다시 동결한다. 사용 중인 에디터 강제 종료·잠금 파일 삭제로 실행하지 않는다.

### 인계 카드와 변경 요청

각 인계에는 기능 ID, 기준 코드/계약 버전, 수정 파일과 소유자, 제공 API·자료, 실행한 검사와 미실행 검사, 실제 연결 여부, 알려진 한계, 다음 소비자가 필요한 순서를 적는다. 별도 worktree·새 세션은 이 계획에서 만들지 않는다. 사용하는 경우에도 실행 전에 경로/기준/허용 파일과 통합 방법을 별도로 등록한다.

계약 변경이 필요하면 변경 이유·영향 기능·저장/회귀 사례를 S0에게 제출한다. S0가 영향 담당에게 새 계약을 전달하고 기존 인계의 유효성을 재판정한다. 소비자마다 임의의 보정 코드를 넣어 서로 다른 의미를 유지하지 않는다. 현행 UI/저장 구현의 공유 파일 소유권을 이 계획이 자동으로 가져오지 않는다.

테스트 자료로 HP에 무력화된 환자·처치된 부상을 준비하는 것은 독립 개발에 유효하다. 하지만 실제 사격·의료 명령을 거치지 않은 검사는 G2/G3의 실제 연결 근거로 재사용하지 않는다. 단위 규칙, 실제 World 연결, 빌드, 실제 렌더, 사람 플레이를 분리한다. 제품 및 Unity 검사는 현재 모두 미실행이며 이 문서의 검사 목록 자체는 통과 증거가 아니다.

## 최종 요약과 다음 행동

현재 계획에서 병렬화할 대상은 유지할 기본 전투 내부다. K 뒤 공간/공격, 건강/부상/회복, 장비/방어구/의료 행동으로 나누고 같은 상태의 쓰기와 World/저장/UI 연결은 통제한다. 기본 전투를 확인하기 전 제압·탄약·Fog of War·원정을 병렬로 일괄 착수하지 않는다.

다음은 실제 구현 요청이 있을 때 K의 작은 시험 규칙·인터페이스와 현재 파일 소유권 인계를 확정하는 일이다. 지금 전체 미래 기획이나 여러 기능의 일괄 구현 승인을 요청하지 않는다. 문서 점검 결과는 Status에 기록하고, 작업 배정·구현·Unity 실행은 별도 상태로 남긴다.
