# 250×250 정착지와 폰 작업 표시

2026-11-18 독립 검토를 반영한 최종 구현 계획. 아래 완료 기준은 구현 후 검증할 항목이다.

## 1. 조사와 설계 근거

- 목표는 새 정착지의 로컬 맵 250×250칸이다. 원작의 고급 설정에서 기본으로 표시되는 크기이며 62,500칸에 해당한다. [원작 설정값을 기록한 플레이 사례](https://www.reddit.com/r/RimWorld/comments/pg26vh/)와 [맵 크기 목록](https://rimworldwiki.com/wiki/World_generation)을 참고했다.
- 설치된 원작의 Data/Core/Defs/Effects/Effecter_WorkGeneral.xml은 ProgressBar 효과를 Mote_ProgressBar와 연결한다. 과거 공개된 식물 작업 코드에는 작업한 양을 수확에 필요한 양으로 나눠 대상에 표시하는 예가 있다. 현재 모든 작업의 위치와 가시성 규칙을 실측한 자료는 아니다. [식물 작업 코드](https://github.com/josh-m/RW-Decompile/blob/master/RimWorld/JobDriver_PlantWork.cs)
- Yayo’s Animation 제작 자료는 Work와 Walk를 별도 동작으로 보여 준다. 우리 게임에서는 이 구분을 살려 발의 접점은 고정하고 작업 중 몸체에만 짧은 반복 동작을 적용한다. 각도·주기는 우리 아트에 맞춰 조정한다. [원본](https://steamcommunity.com/sharedfiles/filedetails/?id=2575938407) · [계승판 작업 예시](https://steamcommunity.com/workshop/filedetails/?id=2877292196)

## 2. 독립 검토에서 바꾼 판단

맵·저장, 작업 규칙, 화면 연출을 세 담당자가 같은 작업 트리에서 읽기 전용으로 검토했다. 통합 담당자가 계획서를 작성했다. 아래 결과는 현재 소스에서 확인한 제약과 이후 구현의 통과 기준이다.

| 검토 영역 | 현재 코드에서 드러난 문제 | 최종 방침 |
|---|---|---|
| 새 게임과 저장 | 새 정착지는 32칸 시험 시나리오를 사용한다. 월드와 시나리오 저장 검사에 각각 64칸 제한이 있다. 기존 새 게임 테스트도 32칸을 기대한다. | 새 게임 전용 250칸 생성 경로를 만들고 두 저장 검사가 같은 범위를 사용하게 한다. 32칸 시험용 생성 경로와 과거 파일로 호환을 확인한다. |
| 시작 화면과 진단 | 전체 맵을 화면에 맞추는 초기 줌으로는 폰이 작아진다. Player 진단에는 좌하단 고정 좌표, 전 맵을 정렬하는 장면 선택, 작은 Sandbox로 교체한 뒤 재시작하는 검사가 있다. | 새 정착지에서만 시작 집단을 중앙 근처에 배치하고 읽을 수 있는 줌으로 시작한다. 캡처는 시작 폰 기준 상대 좌표를 쓰고, 실제 250칸 정착지를 저장한 별도 프로세스로 복원한다. |
| 방향과 복원 | 월드가 바뀌면 화면의 마지막 이동 방향 기록이 비워진다. 조리 작업 칸은 화로 남쪽으로 고정된다. | 인접 작업은 대상 좌표에서 방향을 매번 구한다. 같은 칸은 일관된 정면을 사용한다. 조리는 북향, 사방은 다른 실제 인접 작업으로 검사한다. |
| 시간과 아트 | 렌더링은 일시정지 중에도 갱신된다. 몸체 스프라이트의 피벗과 발 접점이 일치한다는 보장이 없다. | 게임 틱과 틱 사이 누적 시간으로 몸동작을 계산한다. 발을 회전 중심으로 쓰고 게이지 채움은 실제 작업값만 읽는다. |
| 막대와 이름표 | 화면 이름표는 경로선과 다른 이름표를 피하지만 작업 막대 영역은 모른다. | 대상 상단에 막대를 고정하고 그 화면 영역을 이름표 배치에서 비워 둔다. 작업 중 청사진의 중복 진행 숫자는 막대와 겹치지 않게 정리한다. |

## 3. 기능별 구현과 통과 조건

### 1단계. 250×250 정착지를 시작하고 다시 열기

- SimulationRunner.StartNewSettlement에 전용 시나리오를 연결한다. 시작 폰, 침대, 자원, 채집물과 장애물에 같은 좌표 이동을 적용해 기존 접근 관계를 보존한다. 대상은 맵 크기이며 원작의 지형 생성·자원 분포 재현은 별도 기획이다.
- 제목 화면과 게임 중 새 정착지 양쪽에서 생성한다. 첫 화면에 시작 폰과 근처 자원이 보이고 개별 폰을 선택할 수 있어야 한다. 줌아웃과 네 모서리 카메라 이동, 0·249 좌표 입력과 경계 밖 거부를 확인한다.
- 월드와 시나리오의 저장 검사는 각 축 1~250을 허용하고 불일치·251·범위 밖 좌표를 거부한다. 저장소의 기존 10칸 legacy-v1.json과 변경 전 빌드로 저장한 32칸 슬롯을 연다. 새 250 맵에서 가장자리 이동과 변경된 타일을 포함한 이름 있는 슬롯을 저장하고, Player 종료 후 다시 열어 크기·폰 위치·지형·진행 중 상태가 일치해야 한다.
- 기존 32칸 테스트는 시험용 시나리오 검사와 새 게임 진입 검사로 나눈다. 진단 장면이 시험 맵으로 교체된 뒤 찍혔는지도 기록한다. 근거는 SimulationRunner.Slots.cs의 StartNewSettlement, SaveValidation.cs의 World.Size와 Scenario.Size, WorldMapView.Bind, SettlementPlayerCheck의 캡처·재시작 분기다.

### 2단계. 큰 맵에서 기존 조작의 비용 확인

- 같은 PC·빌드 설정·배속·폰 수로 32/250 맵의 첫 표시, 근거리와 끝에서 끝까지의 이동, 여러 폰 동시 명령, 막힌 경로, 한 칸 건설·철거를 측정한다. 도달 불가 시험은 도착 칸을 비워 두고 주위 네 칸을 막아 실제 탐색이 발생하도록 한다. 장거리 작업 후보 조회와 큰 저장·재배 구역 드래그도 확인한다.
- Windows Player에서 첫 표시 시간, 명령~응답 시간, 가장 긴 프레임, 할당량, 지형 전체 갱신 횟수, 슬롯 크기를 입력과 함께 남긴다. 경로 탐색 호출 횟수만으로 비용을 추정하면 작업 진단이 직접 호출하는 ReadPath가 빠진다.
- 통과 기준은 명령 누락 없이 같은 입력에서 같은 경로·결과가 나오고 대표 장면에서 입력 정지가 재현되지 않는 것이다. 한 칸 변경마다 62,500칸을 다시 그리는 경로는 분리해, 초기 바닥은 일괄 채우고 이후에는 달라진 칸만 갱신하는 것을 확인한다. 대표 입력에서 병목이 재현되면 원인을 한 가지씩 수정하고 같은 조건으로 재측정한다. 저장 파일 16MiB와 직렬화 한도는 그대로 검사하고 실제 초과 여부를 기록한다.

### 3단계. 조리 한 사이클로 공통 표시 검증

맵과 작업 표시는 독립적으로 시작할 수 있다. 1·2단계는 저장 복원과 규모 검증 순서이며, 3·4단계는 작은 결정적 시나리오에서 먼저 개발해 마지막에 실제 250칸 정착지에서 합친다.

작업 선택·경로 탐색·진행을 실행하는 함수와 분리된 읽기 전용 조회를 시뮬레이션에 둔다. 반환값은 현재 작업자와 행동 ID, 작업 단계, 대상 ID와 위치, 진행량·필요량, 작업이 실제 진행 가능한 상태다. 화면에서 조회를 여러 번 해도 경로 탐색 횟수, 예약, 진단 이유, 저장 내용이 바뀌지 않아야 한다.

다른 폰이 후보를 조회할 때도 대상의 Reason이 바뀔 수 있다. WorkingFeature 또는 그 사유 한 값으로 활성 표시를 정하면 작업 중인데도 깜빡일 수 있다. 조리 출력의 용량·점유와 건설 현장의 점유는 진행 규칙과 같은 읽기 전용 판정을 공유한다. 현재 폰 ID와 행동 ID가 예약 소유자와 일치하는지도 확인한다. 다른 폰의 후보 조회 전후로 실제 작업이 같으면 표시 역시 같아야 한다.

- 운반 중 → 화로 남쪽 작업 칸 도착 → 실제 조리 → 식사 생성 → 운반 순서로 검사한다. 화로 본체로 방향과 막대 위치를 구하고, 해당 화로에서 실제 실행 중인 계획서의 값만 읽는다. 일시중지된 첫 행과 실행 중인 둘째 행이 서로 다른 진행량을 갖는 사례도 포함한다.
- 실제 조리에서만 몸체와 막대를 켠다. 20/40은 정확히 50%이며, 완성 판정 틱에 1끼가 만들어지고 표시가 사라져야 한다. 100% 표시를 위해 완료 상태를 연장하지 않는다. 산출 위치 포화 등으로 실제 증가가 막힌 경우에는 동작과 막대를 숨기고, 작업이 재개되면 보존된 값에서 표시한다. 게임 일시정지는 같은 작업 장면을 동결한다.
- 월드 교체·행동 교체 때 예전 표시를 제거한다. 같은 화로의 다른 계획서, 다른 폰, 저장 복원 뒤에도 해당 작업의 현재 값과 일치해야 한다. 표시를 호출한 실행과 생략한 실행의 같은 틱에서 생산량, 작업 완료 틱, 점유와 저장 상태를 비교한다.

### 4단계. 다른 작업과 애니메이션 적용

| 실제 작업 | 대상 및 진행값 | 자세와 방향 |
|---|---|---|
| 조리 | 활성 계획서의 Progress / CookingRules.Duration, 화로 본체 | 화로를 향해 작게 숙였다 돌아온다. |
| 건설·철거 | 청사진 Progress / Duration, 건물 DemolitionProgress / DemolitionDuration | 대상 방향으로 내리친다. 인접 네 방향에서 각각 도착한 후의 방향과 좌우 반전을 검사한다. |
| 파종·수확 | 작물 칸의 SowProgress / SowDuration 또는 HarvestProgress / HarvestDuration | 같은 칸에서 정면을 보고 아래로 숙인다. 작물의 자연 성장에는 표시가 없다. |
| 벌목·식물 채집 | 지정 자원 노드의 Progress / Duration | 같은 칸에서 정면을 보고 나무는 내리치고, 식물은 숙인다. 접근 중에는 이동 방향을 쓴다. |

- 진행률은 해당 규칙과 데이터에서 읽는다. 애니메이션 위상은 시뮬레이션 틱과 PendingSeconds로 계산하고 폰별 고정 오프셋을 둔다. 이미 적용된 배속을 다시 곱하지 않는다. 정지 중 여러 프레임의 자세·게이지 동일, 한 틱 수동 진행, 1·3배속에서 같은 게임 시각의 자세 일치를 검사한다.
- 발 접점을 중심으로 몸체만 변형한다. 기본 및 교체 피벗에서 투영한 발의 이동 오차 1픽셀 이내, 논리 좌표·선택 테두리·게이지 앵커 불변을 계획 기준으로 둔다. 중단·완료 뒤 이동·수면 자세로 바뀔 때 이전 회전이 남지 않아야 한다.
- 대상 상단에 왼쪽부터 차는 막대를 배치한다. 기본 줌에서 읽을 수 있는 최소 화면 폭을 정하고 멀리 축소했을 때 서로 겹치면 선택된 작업자의 막대를 우선한다. 1280×720/UI 150%와 1920×1080/UI 100%에서 인접 두 작업, 청사진 숫자, 이름표, 선택 경로, HUD 가장자리 장면을 비교한다. 같은 칸에서 작업하는 폰의 몸체가 막대를 가리지 않아야 한다.

## 4. 최종 수락과 검증 순서

1. EditMode에서 크기 경계, 기존 파일 호환, 작업별 진행값과 조회 무부작용, 중단·재개를 확인한다. PlayMode에서는 실제 새 게임 메뉴, 여러 계획서, 방향과 막대 채움, 정지·배속·수동 한 틱, 작업이 끝난 뒤 표시 제거를 확인한다.
2. Windows 빌드에서 실제 250칸 슬롯 저장 → 종료 → 별도 프로세스로 복원 → 같은 시점부터 한 작업 완료까지 검사한다. 작은 기존 슬롯과 새 슬롯은 별도로 확인한다. 위 성능 측정과 진단 렌더는 실행 조건과 함께 남긴다. 큰 구역은 미리보기·확정·첫 표시·저장을 나눠 측정한다. 파일 한도 초과는 명시적으로 실패하고 이전 슬롯이 다시 열려야 한다.
3. 기본 줌에서 접근·작업 중간·완료 직후의 여러 프레임을 비교한다. 실제 플레이에서는 첫 화면에서 폰 찾기, 폰이 바라보는 대상 알아보기, 근접한 두 작업의 막대 구분, 3배속에서 떨림이나 발 미끄러짐 여부를 확인한다. 자동 결과와 사람의 체감 수락을 따로 기록한다.
4. 작업 배정 시 맵 생성·저장, 시뮬레이션 조회, 화면 표시를 분리하고 WorldMapView 및 공용 통합 테스트 파일은 한 담당자가 편집한다. Unity 검사와 빌드는 소스 쓰기를 동결한 뒤 통합 담당자 한 명이 직렬 실행한다. 구현 결과와 실제 측정, 직접 확인할 항목은 [검증 기록](../Verification/2026-11-18-settlement-work-feedback.md)에 모았다.
