# S0 통합 세션 작업 지시서

상태: G0-D 명세 준비 이후 G0-C 공통 연결을 구현했다. 검사 결과와 실제 제공 API는 [G0-C 검증·인계](../../Verification/2026-11-15-g0-c.md)를 따른다. 후속 사용자 승인으로 건설/재배를 병렬 통합했다. 최신 결과는 [건설·재배 검증](../../Verification/2026-11-15-construction-farming.md)을 따른다. 조리/작업계획/저장은 아직 착수하지 않는다. 제품 기준 `d0069af`, 공통 계약 `settlement-five-v2`. 전역 문서와 실제 진행 상태를 관리할 유일한 통합 담당이다.

## 시작할 때 읽기

[현재 상태](../../Status.md), [현재 범위·소유권·순서](../SettlementFiveFeatures.md), [공통 계약](../../Contracts/SettlementFiveFeatures.md), [기능A](FeatureA.md), [기능B](FeatureB.md), 기존 즉시 명령/점유/물류 계약을 읽는다. 실제 Git 상태와 작업 폴더를 확인하고 미커밋 문서를 보존한다. 전체 로드맵의 후반 기능을 현재 작업에 추가하지 않는다.

## 맡을 일과 수정 권한

현재 계획의 S0 공유 파일 표가 허용 범위다. World의 명령/ID/물자/작업 실행·취소·시간, Runtime 연결, 기존 Presentation의 등록/배치/입력, Scene/Bootstrap/설정/asmdef/검사 manifest를 담당한다. SA/SB 전용 파일은 검토하고 변경이 필요하면 소유자에게 요청한다. 공통 계약과 실제 접점을 맞추는 데 필요한 최소 변경만 한다.

실제 Unity 실행·통합 판정·전체 Status/Decisions 갱신도 S0만 한다. 코드가 어느 세션의 소유인지 불명확하면 쓰기 전에 소유권을 등록한다. SA가 저장을 만들 때 기존 SimulationRunner의 월드 교체·새 화면 연결은 S0이 맡는다.

## G0-D 확정 결과

[준비 확정서](../G0-Preparation.md)에 작업 공간 구성, 실제 코드 접점과 추가할 API, 시험 수치, 시설/출력/조작·저장 규칙을 고정했다. S0 현재 폴더 유지+SA/SB 별도worktree를 기능 착수 때 구성한다. 현재 새 작업 공간/세션은 생성하지 않았으며 제품 파일은 불변이다.

## 다음 G0-C 지시

1. 별도 구현 요청 후 준비 확정서의 공간 구성대로 실행한다. 기능worktree의 실제 절대 경로/기준과 최신 미커밋 문서 인계 해시를 카드에 기록한다. 새 세션 생성과 커밋은 해당 실행 승인 범위를 따른다.
2. v2의 확정 수치/조작/저장 표를 사용한다. 규칙을 변경해야 하면 영향 세션/검사와 함께 버전을 갱신한다. 미정으로 되돌리거나 임의 다른 기본값을 쓰지 않는다.
3. 준비 확정서의 후보 조회/시작/중단/진행/물자 이전/시설 조회/저장 명세를 구현 단계에 연결한다. SA/SB가 사용할 동일한 최소 기반을 제공한다. 빈 스텁을 제공한 사실만으로 검증했다고 쓰지 않는다.
4. 기존 기능을 유지하는 접점 검사와 전체 회귀를 실행하고, 두 기능 담당의 계약/허용 파일 확인 후 1차 구현을 배정한다. 모든 미래 기능을 G0에서 구현하는 프레임워크 작업으로 확대하지 않는다.

## 단계별 통합 지시

| 단계 | 받는 결과 | 연결 순서 | S0의 확인 |
|---|---|---|---|
| 1차 | SA B1/B2/B3, SB F1/F2 | 건설 지정→자재→시설, 재배 구역→성장/수확 | 진짜 자재 소비, 새 침대 사용, 벽/문 통행, 수확물 기존 운반. G1/G2 |
| 2차 | SA C1/C2, SB J1/J2 | 실제 조리대/수확물→생산→모든 작업의 개인 정책 연결 | 한 회 소비/산출, 목표/출력 포화, 개인 끄기/우선순위, 생활/R 우선. G3/G4 |
| 3차 | SA S1/S2, SB I1/I2 | 저장 데이터/파일→후보 월드 검증→교체→화면 재연결→전체 흐름 | 진행·물자·설정 복원, 잘못된 파일에서 기존 월드 보존. G5 |

단위 하나가 준비되면 순서/의존성에 맞게 검증한다. 두 세션의 모든 코드가 끝날 때까지 기다릴 필요는 없다. 공유 폴더에서 아직 컴파일 불가능한 변경이 섞여 있으면 검사 가능한 기준을 먼저 구성하고 동결한다. 검사 기대치를 임의로 낮춰 통과시키지 않는다.

## 검증과 실패 처리

- 기능별 관련 EditMode/PlayMode, G 경계 전체 회귀와 Windows 빌드·Player·렌더를 실행한다. 기존116개는 현재 기준 수이며 새 검사 추가 후 이름 manifest도 갱신해 누락/0개를 막는다.
- 입력 동결을 명시하고 해시를 기록한다. worktree가 분리돼도 Unity 실행 큐는 하나다. 다른 폴더의 독립 작성만 계속할 수 있다.
- 실패하면 단위/입력/관측/기대/소유자를 적어 돌려준다. 실제 다른 기능과 연결하지 않은 개별 검사를 통합 성공으로 보고하지 않는다.
- 사용자에게는 실행 경로와 핵심 조작3~6개·정상 결과를 제공한다. 자동 검사·PNG 확인·사람의 조작 확인은 따로 기록한다.
- 완료 시 제품/검사/문서 범위와 알려진 문제를 검토하고 커밋을 제안한다. 별도 승인 없이는 커밋·merge·cherry-pick·원격 연결·push를 하지 않는다.

## 진행 기록

현재: G0-C 인계 후 건설·재배의 구현과 통합 자동검증을 수행했고 세 역할/세 작업 공간을 사용했다. 커밋 승인 없음. 다음 행동: 최종 동일 기준을 양쪽에 인계하고 사람 확인 결과를 반영한다. 조리/작업계획은 별도 착수 지시 전 진행하지 않는다. 단위 인계 때 [작업 카드](../SettlementFiveFeatures.md)를 채우고 통합 기준을 SA/SB에 전달한다. 임의 세션 추가나 범위 확대는 하지 않는다.

건설·재배 인계와 소유권 확장은 [실행 카드](ConstructionFarming-Handoff.md)에 기록했다. 최종 기준은 통합 검증 문서/manifest이며 feature worktree도 이 기준으로 재동기화한다. 미커밋 상태를 보존하며 임의로 commit/merge/cherry-pick하지 않는다.
