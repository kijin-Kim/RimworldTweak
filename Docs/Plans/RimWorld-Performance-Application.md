# 프로토타입 우선 구현과 측정 기반 성능 개선 지침

확정 지시 반영: 2026-11-17. 적용 대상: 이후 기능 구현을 맡는 에이전트. 상태: 지침 확정, 제품 변경과 성능 실측 미실행.

## 결론과 작업 순서

**현재 범위의 프로토타입을 먼저 구현한다. 기존 코드의 책임과 상태 소유권을 유지하고, 연결된 프로토타입의 실제 성능을 측정한 뒤 필요한 부분만 상세 개선한다.** 확장성은 나중에 문제가 확인된 계산을 찾아 바꿀 수 있는 정도로 제한한다. 미래 부하를 이유로 캐시, 범용 인터페이스, 계측 프레임워크를 먼저 만들지 않는다.

진행 순서는 **기능 구현과 정확성 검사 → 대표 Player 측정 → 병목 확인 → 한 가지 최소 개선 → 같은 입력으로 결과와 성능 비교**다. 문제가 없으면 최적화하지 않고 기능 개발을 이어간다. 기존 P0 전체 계측과 P1 UI 진단 개선을 첫 구현 범위로 삼았던 순서는 폐기한다.

현재 프로토타입 범위는 [저장과 UI 및 아트 계획](SaveLoad-UX-Art.md)의 승인된 사용 흐름이다. 실행 → 정착민/시설 선택 → 작업 지정과 진행 → 저장 → 복원을 연결하고 관련 기능 검사를 통과한 Player를 측정 출발점으로 삼는다. 사람의 조작·가독성 확인은 별도로 남겨도 기술 측정은 진행할 수 있다. 자급 유지, 전투, 장기 로드맵 완성이나 대규모 지원 사양 확정을 새 선행 조건으로 넣지 않는다.

이번 요청은 지침과 계획의 문서화다. [상태](../Status.md), [결정](../Decisions.md), [구조](../Architecture.md), [검증](../Testing.md), [문서 운영](../Workflow.md)을 함께 따른다. 세 검토자의 독립 의견과 반론 교환은 [토론 및 반영 기록](../Reviews/2026-11-17-prototype-performance-review.md)에 있다.

## 프로토타입 구현 때 지킬 최소 구조

새 프레임워크 대신 현재 구조를 보존한다. 아래는 별도 리팩터링 과제가 아니라 기능을 추가할 때의 판단 기준이다.

| 지킬 기준 | 구체적 적용 | 지금 추가하지 않을 것 |
|---|---|---|
| 규칙과 화면 분리 | Simulation이 논리 위치·욕구·수량·진행을 소유하고 화면은 조회와 명령 전달만 수행. noEngineReferences 유지 | ECS 전환, 전체 상태 복제, 별도 엔진 |
| 상태 변경 경로 유지 | 후보 조회 뒤 시작 직전 대상·예약·ActionId 재검사. 물자 이전과 취소는 기존 공통 경로 사용 | 범용 트랜잭션, 기능마다 별도 예약 관리자 |
| 계산을 찾을 수 있는 경계 | ReadPath, PrepareWorkContext, ChooseStorage, 진단 조회의 역할 유지. 검색 코드를 UI 등에 복제하지 않음 | 미래 구현을 위한 인터페이스·DI·플러그인 계층 |
| 수명과 데이터 분리 | 안정 ID, 설정과 실행 상태, 저장 DTO와 World 구분. Reset/Load 때 표시·구독 정리 | 전역 정적 캐시, 이중 데이터 모델, 범용 객체 풀 |
| 재현 가능한 규칙 | 기존 고정 Tick, 명령 순서, 동률 선택과 테스트 입력 구성 유지 | 리플레이 엔진, 전 구간 상시 카운터 |

partial WorldState 파일 분리는 상태 소유권의 분리가 아니다. 함수나 작은 타입 분리는 현재 기능의 이해·정확성·검사에 도움이 될 때만 한다. 구체적인 이유 없이 모든 기능을 서비스로 추출하지 않는다.

전체 순회, 단순 BFS, 임시 컬렉션은 정상 동작하고 측정된 문제가 없다면 유지할 수 있다. 이미 존재하는 재사용이나 실패 재시도 제한을 제거할 이유도 없다. 기존 동작을 보존하면서 새 복잡성을 얹지 않는 것이 기본이다.

## 지금 고칠 결함과 나중에 볼 성능 위험

지금 검사하고 고칠 것은 같은 명령의 중복 적용, 자원 복제·유실, 취소 뒤 예약 잔류, Reset/Load 뒤 구독·표시 중복, 무한 루프와 크래시다. 이는 기능 정확성 문제이며 성능 개선 시점까지 미루지 않는다. 관련 기존 EditMode/PlayMode 검사는 계속 수행한다.

측정 전에는 위험으로만 기록할 것은 동일 읽기 계산 반복, 후보마다 경로 계산, 컬렉션 할당, 전역 revision에 따른 재검색이다. 코드 모양만으로 느리다고 확정하거나 캐시를 바로 넣지 않는다.

예외적으로 기능 검사나 조작을 막는 지연이 재현되면 프로토타입 완료 전에도 해당 상황만 측정한다. 입력·환경·막힌 행동·시간을 남기고 직접 원인만 최소 수정한 뒤 기능 구현으로 복귀한다. 이 예외를 전체 구조 개편이나 미래 규모 최적화의 근거로 확대하지 않는다. 메모리 상승만으로 누수라 단정하지 않고 불필요한 참조·중복 구독 등 소유 증거를 확인한다.

## 프로토타입 이후 측정과 개선 절차

### 대표 실행 기준 만들기

연결된 Player와 재현 입력을 보존한다. PC, Unity·빌드 설정, 정착민·자원·맵 규모, 배속, UI 선택, 입력 파일과 변경 내역을 기록한다. 목표 PC와 대표 규모는 측정 단계에서 구체화하되 미정이라는 이유로 구현이나 현재 환경 측정을 멈추지 않는다. 사람 확인 대기와 기능 실패를 구분한다. 실패한 기능 구간을 정상 성능 기준으로 삼지 않는다.

### 기존 도구로 큰 비용부터 보기

대표 장면의 프레임 시간, Tick 처리, UI, 할당·GC, 저장 지연을 구분한다. 기존 Unity Profiler 또는 CLI·Player에서 수집 가능한 결과를 먼저 쓰고, 원인이 불명확한 구간에만 필요한 마커·카운터를 추가한다. 전용 CLI와 대규모 부하 장면을 먼저 만드는 일은 요구하지 않는다. UI 자동화는 금지이며 도구가 제공하지 않는 결과는 미검증으로 남긴다.

상세 계측의 근거는 반복되는 느린 프레임, 배속 미달, 지속 메모리 증가 등 관측 증거다. FPS와 Tick/s를 구분한다. 현재 설정의 1배속 10 Tick/s와 3배속 30 Tick/s만으로 화면 반응성이 보장되지는 않는다. 절대 합격값은 목표 환경과 규모에 맞춰 정한다. Deep Profiling의 계측 비용을 출시 성능으로 해석하지 않는다.

### 확인한 문제에 맞는 개선 하나 선택하기

| 확인된 병목 | 그때 비교할 선택지 | 함께 검증할 조건 |
|---|---|---|
| UI 진단 반복 비용 | 호출 빈도 조정, 결과 보관, 제한된 캐시 | 정지 중 명령 즉시 표시. 위치·재료·예약·통행·주문 변경과 World 교체 후 결과 정확성 |
| 후보·저장 목적지 탐색 | 싼 조건의 사전 제거, 같은 출발점 검색 공유, 필요 시 공간별 목록 | 우선순위·동률·도달 불가 결과, 시작 전 재검사와 물자 보존 |
| 탐색 임시 할당 | 한정된 버퍼 재사용 | 이전 경로를 덮어쓰지 않음, World 간 격리 |
| 실패 재검색 집중 | 관련 변경 범위 축소, 재시도 분산 | 기존 제한을 중복 구현하지 않음, 반응 시점 변경 명시 |
| 누적 Tick 지연 | 프레임당 처리량 제한과 누적 관찰 | Tick을 조용히 버리지 않음. 실제 배속과 지연 구분 |
| 복원·장기 메모리 증가 | 확인된 참조·구독·캐시 소유 경로 정리 | 이전 World 수명, 복원과 실패 시 현재 상태 유지 |

이 표는 의무 작업 목록이 아니라 선택지다. 단순 BFS로 충분하면 유지한다. 캐시를 택하면 그때 무효화 설계를 작성하고 캐시 없는 기준과 비교한다. 병렬화·ECS·계층 경로·엔진 교체는 기본 해법이 아니며 별도 근거와 범위 검토가 필요하다.

### 전후 비교와 종료

동일 PC·빌드 설정·입력에서 준비 구간을 제외한 전후 측정을 반복한다. 반복 수와 기간은 변동과 문제에 맞춰 정한다. 평균 외에 지연 분포·최대값·작업량을 기록하며 측정 오차와 겹치면 효과 불명으로 보고한다.

규칙 보존이 필요한 개선은 동일 Tick의 위치·욕구·작업·점유·자원·복원 결과를 비교한다. 카운터와 실시간은 규칙 상태에서 제외한다. 반응 시점이나 작업 선택을 바꾸면 순수 최적화가 아닌 규칙 변경으로 구분한다. 관련 검사와 대표 실행이 통과하면 종료하며 새 실패나 근거 없이 검사 범위를 계속 늘리지 않는다.

## 후속 에이전트 판단과 인계

1. 현재 기능에 필요한 수정이면 기존 경계 안에서 단순하게 구현한다.
2. 규칙·소유권·수명을 깨뜨리면 지금 수정하고 기능 검사로 확인한다.
3. 미래 성능만을 위한 코드는 만들지 않고 측정 후보와 이유만 남긴다.
4. 현재 기능 확인을 막는 지연이면 해당 상황만 측정하고 최소 수정한다.

실제 성능 작업 인계에는 재현 입력, 환경·원본 수치, 사용자 영향, 최소 변경과 대안 제외 이유, 규칙 검사, 전후 수치, 완료/미완료/미검증을 남긴다. 기존 검증 기록과 도구를 재사용한다. 새 검사를 추가할 때만 기대 검사 목록을 갱신한다.

기존 진입점은 `pwsh -File Tools/Run-Tests.ps1 -Platform EditMode`와 `pwsh -File Tools/Run-Tests.ps1 -Platform PlayMode`이며 한 명이 순차 실행한다. 이번 문서 작업에서는 실행하지 않았다. 빌드·실행 인자는 Tools/Run-Demo.ps1과 최신 검증 문서를 읽고 사용한다.

과거의 300회 UI 갱신, 30회 복원, 30분 부하, 5회 A/B, 128×128 맵·30명은 필수 완료 기준이나 지원 규모에서 제외한다. 문제가 확인되면 적절한 시험값을 새로 정한다. 상세 계측·캐시·검색 공유·장기 검사를 모든 기능의 완료 관문으로 삼지 않는다.

Computer Use와 우회 UI 자동화 금지, Unity 실행 중 입력 동결과 직렬 실행, 열린 에디터 강제 종료 금지, 커밋·원격 게시 별도 승인 원칙을 유지한다. 실제 조작 확인은 그 시점의 실행 파일 경로·조작·기대 결과와 함께 요청한다. 이 문서가 병렬 에이전트 자동 실행을 지시하지는 않는다.
