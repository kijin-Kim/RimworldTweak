# 건설부터 저장·불러오기까지의 커밋 구성 제안

2026-11-16. 기준 HEAD `d0069af439e0bccfd7d99f56bdd464965991ab12`. 통합 작업 공간 `E:\Dev\RimworldTweak`. 사용자가 4개 구성의 재구성·중간 검증·커밋을 승인했다. 실행 결과는 [커밋 검증 기록](../Verification/2026-11-16-four-feature-commits.md)을 따른다. 원격 연결·push는 하지 않는다.

## 권장 결론

공통 작업 기반 → 건설·재배 → 조리·개인 작업계획 → 저장·불러오기의 **4개 커밋**을 권장한다. 기능마다 별도 커밋을 만들 수도 있지만, 현재 건설/재배는 Production 연결 파일을, 조리/개인 작업계획은 후보 선택·진단·설정 UI 및 연결 검사를 공유한다. 각각을 더 나누려면 검증한 적 없는 임시 연결 상태를 추가로 만들어야 한다. 실제 통합 검증 경계에 맞춘 네 묶음이 검토·되돌리기와 검증 비용을 균형 있게 유지한다. 하나의 대형 커밋보다 문제 발생 지점을 좁히기 쉽다.

사용자가 결정할 사항은 이 4개 구성으로 재구성·중간 검증·커밋을 진행할지 여부다. 2026-11-16 후속 요청으로 실행 승인을 받았다. 다음 기능 전에 이미 확인한 생산·복원 흐름을 독립 기준으로 남기기 적절하다.

## 확인한 변경 범위와 증거

검토 시작 시 tracked 변경 34개(646줄 추가/148줄 삭제), untracked 파일 105개다. untracked는 새 기능 코드·테스트·.meta 82개와 계획·계약·검토·검증 문서 23개다. 본 제안 문서를 추가한 뒤에는 106개(제품82/문서24)다. 문서 갱신 후 수는 달라질 수 있다. Packages/ProjectSettings 변경은 현재 diff에 없다. AGENTS.md의 기존 협업 보고 지침 변경은 제품 변경과 별도로 유지하며 이 4개 제안의 자동 포함 대상에서 제외한다. 삭제·되돌리지는 않는다.

현재 제품 입력 232개의 실제 SHA-256을 저장 검증 manifest와 대조하여 불일치 0개를 확인했다. 제품 집계 해시는 `1945cfb81876394b0f00e5d1cacf8878f3ac395670886ba9bcda00eccd3caab6`이다. 이번에는 제품 코드 수정이나 Unity 검사 재실행 없이 기존 검증 산출물과 현재 입력 일치를 확인했다.

| 공통 작업 기반 | EditMode 86 / PlayMode 36 | 기존 채집·운반·생활과 명령 발급·취소 규칙 |

최종 Windows 빌드 오류0/경고0, 실제 Player 저장·복원과 렌더 이미지 검증을 완료한 기록이 있으며 사용자는 이번 요청에서 전체 정상 동작을 확인했다. 구체적인 실행 ID·시나리오·한계는 각 Verification 문서를 따른다. 최종 EditMode 뒤 Runtime/UI 등 5개 입력 변경은 저장 manifest에 기록되어 있고 최종 PlayMode/빌드/Player로 검증했다. 165개 전체가 최종 바이트에서 재실행됐다는 뜻은 아니다.

이 숫자는 과거 통합 단계의 검사 기록이지, 아직 만들지 않은 4개 커밋의 통과 결과가 아니다. 역사적 입력 manifest는 해시 목록이므로 이전 소스 전체를 복원하는 백업으로 취급하지 않는다. 문서 해시는 당시 검증 시점의 기록으로 유지하며 이번 사용자 확인·제안 문서 변경으로 덮어쓰지 않는다.

## 승인 후 실행·완료 기준

1. 현재 제품·문서·사용자 변경을 별도 보존하고 최종 파일 목록/해시를 고정한다. AGENTS.md, 무관한 변경, 개인 경로/저장 파일, Library/Temp/Builds/TestResults 같은 생성물은 자동으로 포함하지 않는다.
2. 앞 커밋만으로 컴파일·실행 가능한 실제 중간 상태를 구성한다. 최신 공유 파일을 통째로 먼저 넣거나 미래 기능 참조를 빈 구현으로 숨기지 않는다. 테스트·예상 목록·데모·문서도 해당 단계와 맞춘다.
3. S0 한 명이 각 단계의 EditMode/PlayMode, Windows 빌드와 해당 Player smoke를 직렬 실행한다. 실행 중 입력 파일을 동결하고 실행 중인 사용자 에디터를 강제 종료하지 않는다. 실패하면 수정·재검사 후에만 다음 커밋으로 진행한다.
4. 각 단계에서는 점유 획득/취소 해제, 생활·소집 우선순위, 일시정지 즉시 표시와 해당 생산 흐름을 확인한다. 저장 단계에서는 진행 중 건설/재배/조리/운반, 물자·개인 설정·예약 복원 및 손상 파일 거부를 확인한다.
5. 마지막 제품 232개가 승인 시 보존한 제품과 바이트 단위로 일치하는지 대조하고 추가/누락 파일도 검사한다. 문서는 커밋 결과 기록 등 승인된 변경만 허용한다. 중간 재구성 때문에 최종 게임 동작이 바뀌면 완료 처리하지 않는다.
6. 각 커밋 해시·실행 결과를 문서에 기록한다. 사용자 직접 조작 확인은 이미 받은 전체 확인과 구분하며 자동 검사로 새로 받았다고 주장하지 않는다. 원격 연결·push는 하지 않는다.

현재 완료: 변경 범위 검토, 네 묶음 제안, 제품 해시 대조, 사용자 정상 확인 기록. 실행 상태: 중간 상태 재구성·검사와 순차 커밋은 후속 승인으로 진행하며 최신 결과는 커밋 검증 기록을 따른다. 잔여 한계: 실제 디스크 고갈/전원 차단 검사는 수행하지 않았고 기존 종료 시 ComputeBuffer GC 경고는 별도 알려진 항목이다. 자동저장/여러 슬롯/이전 버전 변환과 전투는 현재 범위 밖이다.
